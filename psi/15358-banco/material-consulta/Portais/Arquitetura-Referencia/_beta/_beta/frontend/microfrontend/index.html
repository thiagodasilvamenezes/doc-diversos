    Micro Frontends

    Visão Geral

    A arquitetura de microfrontends permite que aplicações de grande porte sejam compostas por módulos independentes, com escopos funcionais claros e ciclo de vida próprio. Esta abordagem viabiliza escalabilidade, resiliência e agilidade, ao permitir que equipes autônomas desenvolvam, testem e implantem funcionalidades de forma isolada, preservando consistência de experiência, governança corporativa e segurança regulatória.

    Princípios e Imperativos

    • Agilidade de negócio: maximizar a capacidade de inovação, acelerando a disponibilidade de novos produtos digitais sem fricção operacional.
    • Segurança e conformidade: garantir aderência a padrões corporativos, diretrizes regulatórias e exigências legais (incluindo LGPD), adotando controles técnicos explícitos em todas as etapas (código, build, implantação, execução e observabilidade).

    Requisitos de um Microfrontend

    • Deve ser um SPA ou Web Component executado isoladamente em um nó DOM arbitrário.
    • Não deve instalar bibliotecas, fontes ou estilos em escopo global; deve herdar estilos compartilhados e declarar apenas o estritamente necessário para seu escopo.
    • Deve ser agnóstico em relação ao aplicativo HOST (Root Config), com inicialização, montagem e desmontagem bem definidas.
    • Deve poder ser instanciado e parametrizado múltiplas vezes na mesma página, com configurações distintas.
    • Deve cumprir metas de acessibilidade , performance (orçamentos de carga e interação), segurança (CSP, Trusted Types, SRI) e observabilidade (tracing, métricas, logs).

    Benefícios

    • Orientação a domínio (cada MFE foca em um contexto de negócio).
    • Autonomia de times com release ciclos independentes.
    • Escalabilidade organizacional com governança de padrões e interfaces.
    • Resiliência através do controle e isolamento de falhas.

    Single SPA

    O Single-SPA é um framework para reunir vários microfrontends JavaScript em uma única aplicação, tendo em vista auxiliar em atividades tais como:

    • Utilizar diferentes frameworks no frontend, como ReactJS, Angular, Vuejs entre outros.
    • Implantar os microfrontends de forma independente.
    • Melhorar o tempo de carregamento inicial.

    Podemos considerá-lo um meta framework que permite mesclar diversos tipos de framewors/libs Web em uma única aplicação. Por exemplo, conseguimos desenvolver o header de uma página em React, o corpo da página usando Angular e desenvolver o footer com Javascript/HTML puro.

    O Single SPA é composto por um único arquivo HTML(EJS) que é a porta de entrada da aplicação. Esse arquivo importa e registra as aplicações microfrontends através de um javascript que segue uma interface padrão (toda aplicação microfrontend disponibiliza esse arquivo).

    O Single SPA então carrega as aplicações microfrontends sob demanda, ou seja, o framework possui uma camada que realiza o lazy load das aplicações.

    O Single SPA possui libs desenvolvidas nos principais frameworks e bibliotecas JavaScript, porém seguindo a arquitetura de referência de aplicações SPA somente é permitido a utilização do framework Angular para a criação das micro aplicações.

    Padrões e Frameworks

    • Tecnologia padrão: Conforme definido na arquitetura de referência de aplicações SPA, todas as aplicações Micro Frontend do tipo Application devem ser desenvolvidas utilizando o framework Angular
    • Orquestração: uso de Single-SPA para registrar e ativar MFEs por rotas e eventos, mantendo a configuração raiz agnóstica de framework.
    • Composição intra‑framework: quando aplicável, uso de Module Federation (Webpack 5) para compartilhar módulos Angular entre MFEs do mesmo domínio técnico, com controle explícito de versões e compartilhamento.
    • Resolução de dependências: uso de Import Maps no host para controlar o carregamento de módulos ES e dependências compartilhadas em tempo de execução.
    • Módulos utilitários: serviços e design system compartilhados devem ser publicados como utilitários JavaScript/TypeScript puros (não MFEs visuais), versionados e consumidos pelos MFEs.

    Estrutura da aplicação

    Um aplicativo Single SPA consiste de:

    • Root Config: Responsável por renderizar a página HTML da aplicação e carregar e registrar os aplicativos microfrontends Single-SPA. Deve ser criado em Javascript/Typescript puro, se mantendo agnóstico a tecnologias. Cada aplicativo registrado deve possui três informações:

      • Um nome
      • Uma função para carregar o código do aplicativo
      • Uma função que determina quando o aplicativo está ativo / inativo

    • Micro Frontends de Aplicações: Aplicativos SPA ou Web Components customizados com o Single-SPA que devem saber como inicializar, montar e desmontar a si mesmo do DOM. A principal diferença entre um SPA normal e os Single-SPA é que eles devem ser capazes de coexistir com outros aplicativos, já que não possuem sua própria página HTML, coexistindo na página do aplicativo hospedeiro(Root Config).

    • Módulos utilitários: São usados quando precisamos compartilhar uma API em comum com vários microfrontends, por exemplo, ou um design system comum para todas as aplicações, serviços de autenticação, etc. Esse tipo de módulo não é um Micro Frontend, seu único propósito é exportar funcionalidades para uso em outros microfrontends. O Single SPA não suporta a criação de utilitários em Angular, dessa forma esses módulos devem ser escritos em Javascript/Typescript puro.

    Design System

    • O Design System CAIXA (DSC) é o padrão de UI. A camada visual deve seguir Material Design (MD3) e os componentes oficiais do DSC.
    • Acessibilidade e usabilidade: deve sempre ser perseguido o maior percentual de acessibilidade pelos MFEs. Contraste, foco, navegação por teclado, autenticação acessível e ajuda(help) consistente segundo WCAG.

    Segurança

    Os microfrontends devem ser aderentes à Arquitetura de Referência de Segurança da mesma forma que as aplicações SPA comuns, isso significa que o usuário deve ser autenticado no SISET(Keycloak) para obtenção de um token JWT que deve ser utilizado em todas as requisições.

    Porém por se tratar de um tipo especial de aplicação, que é o resultado da coexistência de várias aplicações SPA em um mesmo HOST, algumas restrições são impostas:

    • Todas as aplicações microfrontend devem compartilhar o mesmo token.

    • Todo o código que trata de autenticação e autorização deve estar em um microfrontend utilitário que é compartilhado por todos os microfrontends de Aplicação.

    • Interceptadores para inclusão do header 'Authorization' e guardas de rotas ainda devem existir nos microfrontends.

    Como forma padrão para integração com o SSO, deve ser utilizado o adaptador javascript do keycloak, esse adaptador abstrai algumas complexidades da implementação de uma integração com o SSO.

    Boas práticas:

    • Políticas de Conteúdo (CSP): o host deve impor CSP restritiva (bloqueio de inline script/style, nonces/hashes, frame‑ancestors, upgrade‑insecure‑requests, reporting).

    • Trusted Types: habilitar e requerer Trusted Types para mitigar XSS DOM, com políticas e sanitização explícitas.

    • Subresource Integrity (SRI): exigir integridade para recursos externos (scripts/estilos) quando aplicável.

    • BFF obrigatório: toda comunicação com sistemas internos deve ocorrer via BFFs, com mTLS quando aplicável.

    Bibliotecas Compartilhadas

    Por questões de desempenho e compatibilidade entre as aplicações, é crucial que seu aplicativo da web carregue grandes bibliotecas JavaScript apenas uma vez. Por exemplo, todas as dependências do Angular devem ser carregadas apenas uma vez pela aplicação Root Config e utilizadas por todos os microfrontends.

    Os microfrontends devem carregar apenas bibliotecas que não sejam utilizadas por outras aplicações, e em casos menos comuns, bibliotecas já carregadas pela aplicação Root Config, mas que sejam necessárias em uma versão específica (nesse caso deve ter o cuidado de não haver conflitos entre as versões de uma mesma biblioteca)

    Integração com Microfrontends de Empresas Externas

    A integração de Microfrontends (MFEs) e Backends for Frontends (BFFs) desenvolvidos por empresas parceiras ou integrantes do conglomerado no SIPNC deve seguir um modelo que assegure agilidade e segurança, mantendo conformidade regulatória e mitigando riscos.

    Diretrizes de Integração

    1. Internalização do Código-Fonte: Todo código de MFEs e BFFs deve ser internalizado em repositórios oficiais da CAIXA. É proibida a execução direta de artefatos externos sem ciclo completo de build e validação interna.

    2. Construção Exclusiva em Pipelines Internos: A compilação ocorrerá exclusivamente em pipelines internos, aplicando obrigatoriamente SAST, DAST e varredura de malware. Apenas artefatos aprovados seguirão para implantação.

    3. Fluxo de Integração: O desenvolvimento inicial pode ocorrer no ambiente do parceiro, mas a integração será feita via pull requests ou forks para o repositório raiz da CAIXA, garantindo rastreabilidade e auditoria.

    4. Tecnologia Padrão: MFEs devem ser desenvolvidos em Angular. Uso de outras tecnologias exige aprovação formal da SUART.

    5. Isolamento e Segurança: MFEs poderão ser executados em iframe sandbox, com políticas CSP e comunicação restrita via postMessage, reduzindo riscos de execução de código não confiável.

    6. Comunicação via BFF Interno: Nenhum MFE acessará APIs internas diretamente. Toda comunicação ocorrerá via BFFs internos governados pela CAIXA, utilizando autenticação OAuth2 e API Manager.

    7. Integração com Sistemas Externos: Quando necessário, BFFs farão integração com sistemas do parceiro por links dedicados, sendo vedada a utilização de conexões expostas à internet pública.

    Camadas de Teste

    • Desenvolvimento Inicial: Ambiente do parceiro com mocks fornecidos pela CAIXA.
    • Integração: Pipelines internos com testes de contrato e dados fictícios.
    • Homologação: Ambiente controlado da CAIXA com testes ponta a ponta (MFE + BFF + host).

    Benefícios do Modelo

    • Padronização técnica e regulatória.
    • Mitigação de riscos de segurança.
    • Base para expansão sustentável do ecossistema SIPNC.
    • Garantia de experiência consistente para o usuário final.
