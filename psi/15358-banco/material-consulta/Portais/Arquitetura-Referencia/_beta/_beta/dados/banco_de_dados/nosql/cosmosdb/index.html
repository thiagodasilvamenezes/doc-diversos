    CosmosDB

    Arquitetura de referência de uso restrito

    Importante: Essa arquitetura de referência se encontra em fase de validação e não possui nenhum indicativo de uso geral pelas equipes. Havendo entendimento que ela se encaixa nas necessidades de seu sistema, a SUART deve ser acionada.

    1. Objetivo

      1. O objetivo deste documento é definir a arquitetura referência de infraestrutura para utilização do Cosmos DB na CAIXA, bem como, padrões e tecnologias a serem utilizados, o documento também deve servir como um guia para direcionar a tomada de decisões sobre quando utilizar cada arquétipo arquitetural e avaliar a viabilidade de novos componentes conforme as estratégias de negócios e premissas estabelecidas pela área responsável - SUART.

    2. Conceito

      1. Azure Cosmos DB é um banco de dados NoSQL totalmente gerenciado e sem servidor para aplicativos de alto desempenho de qualquer tamanho ou escala.

      2. O Cosmos DB possui disponibilidade de 99,999%, escalabilidade automática e APIs de software livre para bancos de dados NoSQL como MongoDB e Cassandra.

        1. A escalabilidade automática do Cosmos DB, permite que, mesmo diante de uma carga de trabalho imprevisível a disponibilidade seja sempre instantânea, permitindo leituras e gravações em milissegundos.

      3. APIs de outros DB

        1. API do Core (SQL)

          1. A API do Core (SQL) suporta Java, Node.js, Python, .NET e JavaScript e permite a utilização de SQL para consultas em JSON.

        2. API para Cassandra

          1. Permite a migração e sincronização com o Apache Cassandra por meio da utilização de SDKs, CQL, ferramentas e drivers, possibilita habilitar aplicativos escalonáveis e sem servidor com disponibilidade de 99,999%.

        3. API para MongoDB

          1. Permite a migração e sincronização com o MongoDB por meio da utilização de SDKs, CQL, ferramentas e drivers, possibilita habilitar aplicativos escalonáveis e sem servidor com disponibilidade de 99,999%.

    3. Indicações de uso

      1. Para possibilitar a indicação de uso, a SUART precisa entender o cenário da necessidade do serviço, para isso, as seguintes informações são necessárias:

        • Volumetria estimada da aplicação.

        • Taxa de crescimento estimada.

        • A aplicação irá rodar online ou batch?

        • Qual a performance do banco necessária para a aplicação?

        • Aplicações com necessidade de baixa latência. (usuários e > dados na mesma região).

        • Demandas que utilizem JavaScript como linguagem de consulta.

        • Necessidade de flexibilidade de dimensionamento do banco de > dados (rapidez para incluir e remover recursos conforme a > necessidade).

        • Necessidade de que a aplicação seja compatível com APIs para > bancos de dados NoSQL, formato JSON, banco de dados > família de colunas e chave-valor.

      2. Com as informações em mãos a SUART indicará a melhor solução de banco de dados para a necessidade de negócio.

      3. Fica evidente que a utilização da base de dados dependerá da avaliação de todas as variáveis para possibilitar a escolha mais adequada.

      4. Principais modelos de banco de dados compatíveis o COSMOSDB:

        1. Banco de dados chave-valor:

          1. Quando usar:

            • Alta disponibilidade.

            • Alta performance.

            • Informações unitárias ou em bloco, associadas a uma > chave única (identificador exclusivo).

            • Operações de inserção, atualização e exclusão > baseada na chave.

          2. Quando NÃO usar:

            • Pesquisas que não sejam pela chave (baixo > desempenho)

            • Relacionamentos entre os dados.

            • Consulta por dados (valor).

            • Operações de chaves compostas.

          3. Características:

            1. Capacidade para alto volume de dados: Construído para lidar com uma grande quantidade de dados de forma distribuída, usado para gerenciar petabytes de informações.

            2. Alta disponibilidade: sem ponto único de falha, se um nó específico falhar, os usuários serão movidos automaticamente para o nó de trabalho mais próximo.

            3. Alta performance e velocidade: possui uma arquitetura distribuída ponto a ponto, onde cada nó pode realizar todas as operações de leitura e escrita.

            4. Escalabilidade: a escalabilidade horizontal, simplesmente adicionando máquinas virtuais.

            5. Replicação: por não requer um esquema fixo, torna a replicação mais simples. Permite a replicação entre data centers, o que cria alta tolerância a falhas e perda de dados.

        2. Banco de dados de documentos:

          1. De modo geral os documentos estão relacionados a estruturas de dados JSON, mas em alguns casos podem englobar XML ou outra linguagem de marcação. (qualquer uma que tenha as TAGs)

          2. Quando usar:

            • Registros de logs de API. (Normalmente as API são > JSON, algumas são XML)

            • Grande volume de dados (coleções são fragmentadas em > vários servidores)

          3. Quando NÃO usar:

            • Quando há necessidade de relacionamento entre > coleções/tabelas. (ineficiente)

            • Orçamento limitado (alto custo de replicação e > escalabilidade).

          4. Sem SCHEMA (sem tabelas, linhas e colunas): permite armazenamento de documentos com estruturas distintas em uma mesma coleção.

          5. Alta disponibilidade: banco de dados de documento normalmente apresenta a implementação de alta disponibilidade de maneira mais simples.

          6. Alta performance de leitura: apresenta alta performance de leitura, porém é comum apresentar baixa performance de escrita/atualização.

          7. Atualização parcial: É possível fazer atualização parcial de um documento, porém esse tipo de operação pode apresentar baixo desempenho. Muitos bancos de dados de documento não suportam essa funcionalidade.

          8. Indexação: é possível indexar elementos dentro dos documentos, porém pela natureza dinâmica dos documentos deve ser feita uma avaliação detalhada para verificar a utilização de índices.

    4. Configurações de rede com o Azure Private Link para Cosmos DB

      1. Por padrão, o Cosmos DB é acessível pela internet, que aumenta o risco de vazamento de dados, portanto deve ser configurado o uso do Azure Private Link, em conjunto com as regras de network security groups (NSG), para conexão à conta do Cosmos DB por meio de private endpoints.

      2. Private endpoint é o uso de endereços IP privados, alocados em uma subnet da rede virtual da CAIXA, assim, o acesso ao Cosmos DB ficará restrito a endereços privados, permitindo o acesso aos recursos on-premises com conexão pelo ExpressRoute ou VPN.

    5. Modelo de Preços do Azure Cosmos DB

      1. O Cosmos DB cobra por operações de banco de dados, armazenamento consumido e gateways dedicados (opcionais) na região habilitada na conta do Azure Cosmos DB.

        1. As regiões habilitadas ficam restritas ao Brasil por força da Instrução Normativa 05/2021 do GSI/PR.

        2. Operações de banco de dados

          1. O Custo de todas as operações de banco de dados é normalizado e expresso como unidades de solicitação (RUs).

          2. O Cosmos DB oferece dois modelos de operações de banco de dados:

            1. Taxa de transferência provisionada -- oferece capacidade de operação de banco de dados predefinidas, medida em RUs/segundo e cobrada por hora. Ela oferece leituras e gravações em milissegundos de dígito único e disponibilidade de 99,999%, sendo ideal para cargas de trabalho grandes e críticas que exigem alta disponibilidade baixa latência garantidas.

            2. Opção sem servidor oferece operações de banco de dados sob demanda e é cobrada pelas RUs usadas para cada operação de banco de dados, esta opção sem servidor facilita a execução de cargas de trabalho com picos que não têm um tráfego mantido e pode lidar com intermitências de tráfego sob demanda, sem gerenciamento nem planejamento de recursos.

        3. Armazenamento Consumido

          1. O armazenamento analítico e transacional é cobrado em GBs consumidos pelos dados e pelo índice, em todas as regiões do Azure para as quais seu banco de dados é distribuído.

          2. Backup contínuo -- cobrado em GBs armazenados em todas as regiões do Azure.

          3. Backup periódico -- É habilitado por padrão, com duas cópias de backup adicionais armazenadas eu duas regiões do Azure (limitadas a regiões no Brasil).

        4. Gateway dedicado

          1. Gateways dedicados são cobrados por hora pelo conjunto de recursos de computação dedicados, com base no número selecionado de núcleos e memória, o gateway dedicado roteia solicitações para as partições de back-end do Cosmos DB e pode ser habilitado para dar suporte a um cache integrado com API do Core (SQL).

    6. Modelo de recurso do Azure Cosmos DB

      1. O Azure Cosmos DB é uma plataforma como serviço (PaaS) totalmente gerenciada, para começar a usar o Azure Cosmos DB, inicialmente deve-se criar uma conta do Azure Cosmos no grupo de recursos e, em seguida, bancos de dados, contêineres e demais itens.

      2. A conta do Azure Cosmos é a unidade fundamental de distribuição global e alta disponibilidade. Sua conta do Azure Cosmos contém um DNS exclusivo e você pode gerenciar uma conta usando o portal do Azure ou a CLI do Azure ou usando diferentes SDKs específicos de linguagem.
