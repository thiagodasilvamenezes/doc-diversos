    Critérios para avaliação de soluções NoSQL

    NoSQL compreende o conjunto de tecnologias de persistência de dados que não seguem o modelo tradicional relacional (tabelas, colunas e chaves). Oferecem estruturas mais flexíveis para lidar com grandes volumes de dados, dados semiestruturados ou não estruturados, e cenários que exigem alta escalabilidade.

    Características principais das soluções NoSQL

    1) MODELO FLEXÍVEL - não adota esquema fixo; pode armazenar documentos, pares chave-valor, grafos ou colunas.

    2) ESCALABILIDADE HORIZONTAL - distribuição em vários servidores (clusters) para aumentar a capacidade da solução.

    3) ALTA PERFORMANCE PARA LEITURA - ideal para aplicações com milhões de consultas simultâneas.

    4) CONSISTÊNCIA EVENTUAL - prioriza disponibilidade e tolerância a falhas, diferente do ACID dos bancos relacionais.

    SQL x NoSQL

    1) Relacionais (SQL) - organizam dados em tabelas, seus relacionamentos são estabelecidos por chaves primárias e estrangeiras. Utilizam linguagem SQL para consultar, inserir, atualizar e excluir dados. São ideais para cenários que exigem transações seguras (ACID) e forte controle de integridade, como sistemas financeiros, ERPs e aplicações corporativas.

    2) NoSQL - conjunto de tecnologias de persistência que não seguem o modelo tradicional relacional (tabelas, colunas e chaves). Podem ser classificados em:

    Documentos: dados armazenados em objetos complexos, tipicamente em formato JSON/BSON (Ex. Azure/CosmosDB, GCP/Firestore).

    Chave-Valor: dados voláteis utilizados como solução de cache e controle de sessões (Ex. Redis, AWS/DynamoDB). Deve ser adotada como solução complementar de persistência (cache) com o objetivo de reduzir a latência na obtenção de dados com baixa volatilidade e alto volume de requisições.

    Colunar: dados tipicamente utilizados para análises de grandes volumes agregados de dados, tipicamente em soluções de Big Data (Ex. Cassandra, HBase, Parquet-Iceberg/Delta).

    Grafos: Para relacionamentos complexos/recursivos (Ex. Neo4j, Spanner, SparkGraph/Databricks).

    Persistência de dados (SQL ou NoSQL) em ambiente de nuvem

    Importante: Soluções de persistência de dados (SQL ou NoSQL) em ambiente de nuvem devem: 1. contemplar o uso de acesso privado. Não devem ser mantidas com acesso publico a internet sob o risco de vazamento de dados da CAIXA. 2. ser hospedadas no Brasil em atendimento à Instrução Normativa 05/2021 do GSI/PR.

    Quando usar SQL (bancos relacionais)

    1) Sistemas transacionais que exigem consistência forte (ACID), como pagamentos, transferências, liquidação e reconciliação.

    2) Compliance e auditoria: soluções que atendam a normas e resoluções de órgãos de controle (BACEN, LGPD, PCI-DSS - Payment Card Industry Data Security Standard) onde trilhas de auditoria e integridade são mandatórias.

    3) Dados estruturados e estáveis: tabelas com esquema fixo, como cadastro de clientes, contas, produtos financeiros.

    4) Relatórios regulatórios e contabilidade: geração de balanços, demonstrativos e obrigações legais.

    Quando usar NoSQL (bancos não relacionais)

    Soluções NoSQL são otimizadas para cargas de trabalho com volume elevado de consultas (leitura) e baixo índice de operações de escrita (inserção, atualização e exclusão). São ideais para cenários onde dados complexos são predominantemente escritos uma única vez e lidos frequentemente.

    1) Dados dinâmicos ou semiestruturados (logs, telemetria).

    2) Preferências do cliente: dados que mudam com frequência ou possuem atributos variáveis (ex. cadastro de dispositivos, notificações, conteúdos favoritos).

    3) Dados não estruturados ou semiestruturados: Imagens, Audio, Anexos, logs, interações digitais.

    4) Cache e alta disponibilidade e baixa latência: aplicações com milhões de usuários (Mobile Banking, Internet Banking, ATM, etc.).

    5) Big Data e Analytics: análise de comportamento, armazenamento para machine learning, prevenção de fraudes.


    Pontos de atenção na adoção de NoSQL

    1) Atualização Parcial - A atualização de campos específicos dentro de um documento pode ser ineficiente. Diferentemente de bancos relacionais, muitos bancos de documentos exigem recuperar todo o documento, a alteração do conteúdo específico do campo e a subsequente atualização integral do documento. Embora plataformas modernas como o Cosmos DB ofereçam recursos aprimorados para patching (atualização parcial), a complexidade e o custo computacional ainda podem ser maiores do que em bancos de dados relacionais otimizados para esse fim.

    2) Impacto de Alterações - A flexibilidade do esquema ("schema-on-read" / "schema-less") não elimina a necessidade de planejamento. A alteração de campos de domínio ou tipos de dados exige atenção, pois pode ser necessário atualizar programaticamente todos os documentos existentes para refletir a nova estrutura - operação lenta e cara em grandes volumes de dados.

    3) Modelagem de Dados e Desnormalização - A modelagem deve focar em desnormalização para reduzir o número de consultas (operações de ida e volta ao banco de dados). Isso envolve incorporar dados relacionados dentro do mesmo documento, aceitando alguma redundância para otimizar o desempenho de leitura, mas aumentando a complexidade em cenários que demandariam atualizações coordenadas de dados redundantes.

    4) Gerenciamento do Tamanho do Documento - Documentos grandes podem impactar o desempenho de leitura e escrita. É importante projetar a estrutura para manter os documentos em tamanhos gerenciáveis, evitando a incorporação de coleções aninhadas excessivamente grandes que crescem indefinidamente.

    5) Relacionar dados de várias coleções - A consulta de dados envolvendo múltiplas coleções em bancos orientados a documentos tende a ser complexa, pois as informações encontram‑se dispersas em diferentes documentos, sem relações estruturadas. A combinação desses dados exige múltiplas buscas, processamento individual, tratamento de redundâncias e, muitas vezes, não há critérios explícitos de relacionamento entre as coleções. Em contraste, bancos de dados relacionais oferecem relacionamentos nativos e eficientes, permitindo consultas baseadas em chaves definidas, o que simplifica significativamente a recuperação das informações.

    Considerações relevantes

    Bancos relacionais modernos possuem suporte a JSON/XML. Estes SGBD podem ser considerados relacionais estendidos ou SGBD hibrido (relacional + multimodal). Como exemplos, tanto Oracle quanto DB2 permitem manipular e armazenar dados complexos como XML e JSON.

    Suporte a XML - Oracle suporta XMLType desde a versão 9i, com limitações. Desde então tem apresentado melhorias de performance na indexação e novas funções de manipulação de XML. IBM DB2 introduziu tipo de dados XML (pureXML) no Db2 z/OS versão 9. Desde então a IBM introduziu melhorias de performance e novas funções para integração do tipo XML com a linguagem SQL.

    Suporte a JSON - Oracle oferece suporte nativo ao JSON a partir da versão 12c, embora tenha introduzido um tipo de dado nativo para JSON apenas na versão 21c (OSON). IBM Db2 z/OS possui funções nativas para manipular JSON (ex. JSON2BSON, BSON2JSON, JSON_VAL, JSON_LEN, JSON_TYPE e JSON_TABLE) desde a versão 12. Não existe um tipo nativo específico para JSON, embora documentos JSON possam ser persistidos em formato BSON (formato binário padrão para dados JSON) que são armazenados em atributos do tipo BLOB).

    Quando usar XML/JSON em bancos relacionais

    • Dados complementares (volume moderado): quando os documentos são usados como extensão de registros relacionais (ex.: detalhes adicionais de cliente).

    • Necessidade de transações ACID: se os documentos fazem parte de uma operação crítica (ex.: documento em XML vinculado a uma transação, recibo de transmissão de obrigação legal).

    • Integração com sistemas legados: quando o ecossistema é fortemente baseado em SQL.

    • Governança e compliance centralizados: auditoria, trilhas e segurança exigem um único ponto de controle.

    • Consultas relacionais complexas: quando os documentos precisam ser correlacionados com tabelas relacionais.

    Ao optar por armazenar dados complexos em formato XML/JSON em banco relacional deve-se levar em consideração o seguinte:

    1) Documentos devem possuir no máximo 10 KB para consultas eficientes (Melhor desempenho no parsing, menor custo de indexação, menor complexidade de operações de manutenção/migração – reorganização, atualização de estatísticas, custo de backup e replicação).

    2) No caso de tabelas com grande volume de dados (registros muito grandes ou muitos registros) deve-se realizar prova de conceito com o objetivo de comprovar a viabilidade da estratégia no caso concreto.
