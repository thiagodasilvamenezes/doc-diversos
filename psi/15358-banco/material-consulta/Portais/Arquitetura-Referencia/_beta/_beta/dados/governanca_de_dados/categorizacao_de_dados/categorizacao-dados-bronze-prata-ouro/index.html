    Arquitetura de referência de uso restrito

    Importante: Essa arquitetura de referência se encontra em fase de validação e não possui nenhum indicativo de uso geral pelas equipes. Havendo entendimento que ela se encaixa nas necessidades de seu sistema, a SUART deve ser acionada.

    Análise de Solução

    Dados são o grande ativo das corporações. São fundamentais para o entendimento do mercado, dos clientes e dos produtos; apoiando estratégias e decisões. No entanto, o processo de coleta, processamento, armazenamento e geração de informações estratégicas é bastante custoso e, muitas vezes, não se consegue chegar à informação necessária, devido a forma como os dados foram organizados e armazenados.

    Assim, surgiu o Data Lake [1] [2] em 2010, quando James Dixon [2] apresenta uma alternativa para alguns problemas relacionados a forma como os dados estavam sendo encontrados naquele momento, em Data Marts/Data Warehouses [3], que possuem um padrão de dados estruturados para armazenamento desses dados em silos, o que dificulta as análises mais abrangentes. O Data Lake se apresentou como uma alternativa de repositório para armazenamento e disponibilização em larga escala de uma grande variedade de dados da corporação e são destinados a uma grande variedade de necessidades analíticas e produção de insights para tomadas de decisão inteligentes, já que os dados são mantidos consolidados, integrados, seguros e acessíveis, sejam eles estruturados, semiestruturados ou não estruturados.

    Os benefícios identificados na adoção do Data Lake se devem por várias características, dentre elas, um processo rápido de inserção de dados e de baixo custo, já que não há necessidade de transformar os dados antes deles serem armazenados no repositório, aumentando a capacidade e frequência de atualização dos dados, não necessitando de uma estrutura de armazenamento complexa; a compatibilidade com ferramentas de ciência de dados, já que a ideia é que o Data Lake seja um repositório democrático, que pode receber qualquer tipo de dado, sendo estes oriundos de sistemas internos, de dispositivos menores e de fontes externas, independentemente da frequência de geração, da complexidade e da finalidade, permitindo que as corporações desenvolvam uma infraestrutura eficiente para o processamento de Big Data; a escalabilidade, uma vez que o Data Lake se apresenta como uma solução flexível e escalável, já que os dados são armazenados sem pré-processamentos, a corporação pode adequá-los de acordo com a necessidade e capazes de crescer enormemente, de acordo com a geração de Big Data e, por fim, a colaboração, já que o Data Lake facilita a colaboração entre diferentes membros, inclusive, sem o suporte técnico de TI, pois está mais próximo de um padrão fácil de ser entendido e gerenciado por pessoas com diferentes habilidades, facilitando e democratizando as análises. Compreender os objetivos e benefícios do Data Lake é fundamental para que a TI consiga construir um modelo sustentável de infraestrutura para análise de dados, que permita a instalação de uma cultura de Big Data, inclusive com o uso da nuvem, beneficiando-se de todos os princípios e capacidade da computação em nuvem.

    Assim, algumas vezes, pode-se associar o Data Lake ao Data Warehouse, porém são plataformas com finalidades distintas, apesar de ambos poderem ser repositórios de Big Data.

    Também surgiu o termo Data Lakehouse, que se apropria de características importantes das duas plataformas.

    Dessa forma, temos:

    • Data Warehouse em que os dados são organizados, curados e governados para atendimento de necessidades de negócio;

    • Data LakeHouse [4] [5] [6] em que há “unificação” dos conceitos Data Lake e Data Warehouse.

    Figura 1 Data Lake x Data Warehouse x Data Lakehouse

    Um Data Lakehouse é uma solução de armazenamento aberta e pode atender às necessidades de cientistas e engenheiros de dados, que realizam análises e processamentos mais profundos sobre os dados, bem como as necessidades de profissionais do data warehouse, que coletam e publicam dados para BI e relatórios.

    O Data Lake possui uma arquitetura aberta e escalonável, que pode ser implementada on premises ou na nuvem, e pode armazenar dados de fontes diversas, em formatos diversos, desde dados estruturados (tabelas de banco de dados, planilhas do Excel), semiestruturados (arquivos XML, páginas da Web) até não estruturados (imagens, arquivos de áudio, tweets), em estado bruto, sem tratamento prévio, exatamente como eles são nas fontes, sem vincular à nenhuma necessidade específica inicialmente. À medida que surge a necessidade de uso desses dados, os objetivos vão sendo definidos.

    Os usuários acessam e exploram livremente os dados no Data Lake, sem precisar movê-los para outro sistema, e isto acontece geralmente de forma ad-hoc. Com isto, os Data Lakes exigem governança, metadados técnicos e negociais e manutenção contínuos para que os dados possam ser utilizados em uma variedade de aplicativos, habilitando a análise de Big Data, consultas SQL, mineração de texto, análise de streaming, aprendizado de máquina, análises preditivas e outras formas de ação inteligente, tais como, o cruzamento de fontes distintas a fim de se obter insights e valiosas informações estratégicas, permitindo a construção de uma cultura de dados.

    Arquitetura implantada (ATUAL)

    Em 2017, a CAIXA iniciou o seu projeto de Big Data na iniciativa Arco Digital. A iniciativa não permitia aquisição de software devido a restrição de custo imposta à época.

    Assim, dentre as opções dos softwares disponíveis e soluções opensource, foi selecionada a plataforma Hadoop, de distribuição Hortonworks: HortonWorks Data Platform (HDP) [7]. Para o storage foi identificado Dell EMC Isilon [8] [9] [10], que provê filesystem utilizando protocolo HDFS (Hadoop File System) [11], apropriado para utilização com Hadoop e compatível com HDP.

    Data Lake

    Para o Data Lake, a plataforma de armazenamento selecionada deveria comportar o volume de dados esperado. Dessa forma, a escolha do Hadoop se deu exatamente pelo seu filesystem HDFS, devido à sua capacidade de armazenamento de altos volumes, comportando dezenas de petabytes, com tamanhos de arquivos máximos em dezenas de terabytes (centenas em versões mais recentes).

    Os processos de carga do Data Lake se valeram tanto da capacidade de volumetria quanto da escalabilidade horizontal do ambiente, para a construção do Data Lake em banco de dados pseudo-SQL Pivotal HDB HAWQ.

    Ingestão Batch

    No processo de ingestão batch ocorre a ingestão de arquivos CSV [15] em codificação [16] UTF-8.

    Além disso, os arquivos são processados com Apache Pig [17], com escalabilidade horizontal [18] e gerenciado por programa Python [19].

    A principal ferramenta para extração de dados de sistemas transacionais é Informatica PowerCenter.

    Informatica PowerCenter e Informatica PowerExchange

    A ferramenta Informatica PowerCenter [20] realiza o processo ETL [21] [22] [23] [24] de fontes de dados corporativas para produção de arquivos CSV e ingestão por rotinas de ingestão batch do Data Lake.

    • Sistemas Gerenciadores de Banco de Dados (SGBD) [25]: Microsoft SQL Server [26], Oracle [27] [28], IBM Db2 [29], etc.

    • Arquivos: VSAM [30], CSV, JSON [31] e XML [32].

    Atualmente, o projeto de Big Data CAIXA, no qual se encontra o Data Lake, se resume a infraestrutura e conjunto de ferramentas, e existe apenas em ambiente on premises. O objetivo é ampliar suas funcionalidades e se beneficiar das vantagens do ambiente em nuvem, principalmente aquelas relacionadas à análise e disponibilidade dos dados.

    Domínios de Dados

    Na CAIXA, os dados são organizados por siglas de sistema e, conforme MN OR 016 [35], os gestores desses sistemas são os gestores dos dados neles contidos e estes são os únicos entes tacitamente autorizados para acesso aos dados desses sistemas. Isto caracteriza a existência de silos de dados, uma vez que o acesso aos dados de cada sistema é concedido apenas pelos gestores da informação e os entes autorizados (por esses gestores). Os sistemas representam um produto, conjunto de produtos ou aspectos específicos de uma linha de negócio, mas, um único sistema não contém todos os dados que representem uma linha ou área de negócio.

    No entanto, apesar do conhecimento sobre os dados estar contido na área de negócio a eles associada, todo o processo de coleta, transformação e disponibilização dos dados, quando eles são requisitados, está sob a responsabilidade da TI, fazendo com que essas atividades estejam centralizadas em equipes técnicas e não de negócio.

    Para contornar essa situação, é preciso promover a democratização dos dados e o empoderamento das áreas de negócio para tratar os seus dados de acordo com as suas necessidades, tornando-as mais autônomas, pois passam a ser responsáveis por todo o processo de obtenção, tratamento e disponibilização dos seus dados, reduzindo o tempo de manipulação desses dados e aumentando sua confiabilidade, uma vez que estão sendo tratados por quem realmente os compreendem. Com essa abordagem, obtém-se mais autonomia, inovação, qualidade, segurança e agilidade dentro de cada área de negócio, eliminando gargalos de demandas e promovendo processos de análises sobre os dados mais ágeis e assertivos, apenas por valer-se do conhecimento sobre os dados contido nas áreas de negócio.

    Assim, no âmbito CAIXA, os dados não serão mais organizados somente por sistemas, mas por domínios de conhecimento1 também, ou domínios de negócio ou domínios de dados, e serão gerenciados e disponibilizados como produtos para os usuários que deles necessitam. Os domínios de conhecimento ou de negócio ou de dados serão definidos a partir das áreas de negócio da CAIXA, e o acesso a esses domínios de dados estará autorizado a todos os entes que requeiram suas informações, eliminando, assim, os silos de dados. Essa abordagem se utiliza da organização corporativa da CAIXA, composta pelas várias áreas ou linhas de negócios, sob responsabilidade das respectivas vice-presidências.

    Além disso, a CAIXA adotou um novo modelo de atuação da TI, que busca potencializar as entregas de valor, ao considerar o cliente como o foco principal das soluções, e promover uma maior aproximação entre o negócio e a TI CAIXA, buscando agilidade na tomada de decisões, rapidez e eficiência nas entregas e um esforço direcionado por dados.

    Assim, surgiu o conceito das comunidades CAIXA, que materializam esse modelo de atuação da TI, no qual cada comunidade representa logicamente uma ou mais áreas de negócio, no intuito de fortalecer o conhecimento e o empoderamento das áreas de negócio em um esforço multidisciplinar da TI e do Negócio. Consequentemente, todos os sistemas corporativos e seus respectivos dados, associadas às suas respectivas áreas de negócio, ficam sob responsabilidade das comunidades.

    Tabela 1 - Comunidade x Responsabilidade x Portfólio

    Além da organização por área(s) de negócio, as comunidades CAIXA possuem equipes multidisciplinares que atuam dentro de cada comunidade e, dentre os perfis definidos há o dono do produto, que é o gestor dos dados gerados pelos sistemas corporativos, que fazem parte do portifólio de cada comunidade.

    Diante do exposto, e buscando aproveitar-se de toda a organização, estrutura de perfis e modelo de atuação das Comunidade CAIXA, os domínios de dados serão definidos com base nas linhas de negócio atendidas por cada Comunidade CAIXA.

    A grande vantagem dessa estratégia é diluir o esforço de construção/manutenção de pipelines entre os sistemas corporativos e o data lake, permitir que a evolução dos dados entre Bronze, Prata e Ouro possuam processo de gestão de mudança e validação do gestor dos dados.     Data Mesh

    Além da categorização dos dados, é importante observar o conceito de Data Mesh2 [45], que consiste em uma nova abordagem de arquitetura de dados distribuída e descentralizada, organizando os dados em seus domínios de dados, usando uma abordagem derivada do design orientado por domínio e um modelo de propriedade de dados, disponibilizando-os para os demais domínios de dados como produtos da corporação. Os domínios de dados são agrupadores lógicos, de uma mesma área de negócio, por exemplo, contemplando os dados e as equipes gestoras e mantenedoras desses dados, que detém o conhecimento adequado sobre a diversidade das regras de negócio para tratar e manipular os dados, e a velocidade de resposta frente às mudanças nas regras de negócio. Trata-se de equipes especializadas, multifuncionais e independentes, capazes de produzir de forma mais eficiente os resultados esperados pela área de negócio.

    Com isto, não há a necessidade de armazenar e gerenciar os dados em repositórios específicos, que dificultam o acesso e limitam as possibilidades de análises sobre eles. Além disso, a responsabilidade de tratar e disponibilizar os dados, com qualidade e segurança, fica a cargo da equipe de cada domínio de dados, que é responsável por aplicar as visões de negócio e correlações adequadas sobre os dados, e deixá-los disponíveis para uso, criando uma plataforma de dados self-service.

    Essa abordagem permite eliminar os desafios de disponibilidade e acessibilidade de dados em escala e, que os usuários de negócios e cientistas de dados acessem, analisem e gerem insights de negócios, a partir desses dados, sem a intervenção de equipes de TI especializadas que, na maioria dos casos, estão distantes das áreas de negócio da corporação.

    Como visto na figura acima, essa nova abordagem de arquitetura requer um novo modelo de governança de TI, para garantir a interoperabilidade dos domínios de dados e democratização dos dados necessárias, que não podem ser alcançadas sem a descentralização dos dados e a priorização da experiência dos consumidores dos dados.

    A implementação do Data Mesh impõem alguns desafios para as corporações, dentre eles, a reestruturação de suas plataformas de dados, a redefinição das funções dos proprietários dos dados nos domínios de dados e a revisão das estruturas para tornar a nova abordagem viável. Por este motivo, dentro da abordagem do Data Mesh são propostas algumas topologias com o intuito de fazer com que as corporações possam adaptar as suas estratégias de adoção do Data Mesh aos requisitos necessários para a implementação, tais como, definir os proprietários dos dados e domínios de dados, estrutura organizacional, estratégia de migração, tecnologias necessárias etc.

    Em Data Mesh: Topologies and domain granularity [47], Piethein Strengholt propõe desde uma topologia de mesh 100% descentralizada e federada, chamada de fine-grained fully federated mesh, até uma topologia de mesh com domínios de dados distribuídos, mas sem granularidade por domínio de dados. Ainda existe agregações em que diversos domínios não conseguem ser identificados separadamente, chamada de coarse grained and governed mesh. Ou seja, uma topologia 100% centralizada tradicional até alcançar uma topologia completamente descentralizada.

    A seguir, as topologias propostas por Piethein Strengholt são apresentadas:

    • Na topologia chamada Fine-grained fully federated mesh, os dados são organizados em domínios de dados (equipes independentes) a partir do nível de granularidade das fontes de dados, e são totalmente compartilhados entre os demais domínios de dados, sendo também a gestão dos dados distribuídos entre os domínios de dados;

    • Na topologia chamada Fine-grained and fully governed mesh, os dados são organizados em domínios de dados (equipes independentes) a partir do nível de granularidade das fontes de dados, e são compartilhados e geridos por um processo de governança centralizado;

    • Na topologia chamada Hybrid federated mesh, os dados são organizados em domínios de dados (equipes independentes), e são compartilhados e geridos utilizando as duas abordagens anteriores, parte de forma federada e parte de forma centralizada;

    • Na topologia chamada Value chain-aligned mesh, os dados são organizados em conjuntos de domínios de dados, definidos a partir das similaridades negociais entre esses domínios de dados e o valor que, juntos, podem representar. Os dados são geridos e compartilhados pelos próprios domínios de dados;

    • Na topologia chamada Coarse grained aligned mesh, os dados podem ser organizados ou não em conjuntos de domínios de dados, definidos a partir das similaridades negociais entre esses domínios de dados e o valor que, juntos, podem representar. Os dados são geridos e compartilhados pelos próprios domínios de dados;

    • Na topologia chamada Coarse grained and governed mesh, os dados podem ser organizados ou não em conjuntos de domínios de dados, definidos a partir das similaridades negociais entre esses domínios de dados e o valor que, juntos, podem representar. Os dados são geridos e compartilhados por um processo de governança centralizado.

    Proposta Mesh

    Considerando as características do projeto de Big Data da CAIXA, o conceito de Comunidades CAIXA e a maturidade das suas áreas de negócio no uso dos ambientes de dados, a topologia proposta para a organização dos dados no Data Lake é a fine grained governed mesh que seria a evolução natural da atual organização coarse grained governed mesh em que algumas comunidades fazem gestão de mais de um domínio de dados com equipes compartilhadas.

    Fine grained governed mesh permite o agrupamento dos dados em domínios de dados com gestão fina, fazendo uso das equipes de gestão e manutenção dos dados, que já existem nas comunidades, e do conhecimento que as áreas negociais detêm sobre os dados.

    Além disso, essa abordagem se aproveita da existência dos papéis dos proprietários ou gestores dos dados, definidos em cada comunidade, e necessário para a criação do domínio de dados.

    Essa abordagem também facilita o processo de ingestão dos dados no Data Lake, especialmente na camada de dados bronze, pois não requer conhecimento específico do negócio da equipe de TI, responsável pela ingestão dos dados no Data Lake, já que os dados são obtidos e armazenados da forma em que se encontram nas fontes de dados originárias, sem qualquer tratamento que altere esses dados.

    Após o processo de ingestão dos dados no Data Lake, eles passam a ser tratados dentro de cada domínio de dados, pela equipe multifuncional do domino, responsável pela manipulação e disponibilização dos dados. Para garantir a qualidade dos dados e do processo, deve existir um processo de governança centralizado, que define padrões de obtenção, tratamento, manipulação e acesso aos dados, obtém e gerencia os metadados técnicos e negociais, além da garantia de aplicação de processos de qualidade sobre os dados em cada camada de categorização.

      • Esta camada da governança é responsável por garantir a qualidade do dado, atestado a confiabilidade do dado, definindo o ciclo de vida de cada dado e quais dados podem ser considerados para a definição de uma arquitetura de dado mestre e de referência.

    • Segurança dos dados

      • Esta camada da governança é responsável por garantir a segurança dos dados e das informações geradas, ao garantir a implementação do processo de autorização de acesso aos dados dentro de cada domínio de dados, os perfis responsáveis, além de definir o processo de mascaramento dos dados, obedecendo os critérios de proteção dos dados e de permitir a verificação da utilização dos dados por meio de logs de acesso para auditoria.

    • Processos

      • Esta camada da governança é responsável por definir os padrões a serem utilizados no processo de extração e carga dos dados, as ferramentas de orquestração dos processos de atualizações dos dados, as regras para o compartilhamento dos dados entre os domínios de dados e os usuários finais, padrões de criação dos objetos para cada categoria de dados dentro dos domínios de dados e regras de validação dos modelos de dados gerados.

    Dito isto, pode-se observar que a arquitetura proposta compreende as entidades e o processo de governança necessários para a implementação de uma adequação do conceito de Data Mesh, com foco na construção de esteiras de produção de dados, especializados em domínios de dados, e no compartilhamento dos dados a partir de soluções do tipo self service.

    Critérios

    A arquitetura proposta se aplica a todos os dados disponíveis no ambiente CAIXA: sistêmicos, derivados, de origem externa, de Shadow IT etc.

    Todas as informações devem ser organizadas em domínios de dados e categorizadas conforme essa arquitetura de referência.

    Dell EMC Isilon

    O Dell EMC Isilon é uma plataforma de armazenamento NAS scale-out , com integração nativa ao protocolo HDFS, permitindo aos usuários do Hadoop acesso integrado para proteção dos dados da corporação, eficiência de armazenamento e movimentação de dados acelerada em uma grande variedade de protocolos padrão do setor (NFS, CIFS, FTP, HTTP).

    A integração do HDFS ao Isilon também permite aos clientes usar qualquer distribuição Hadoop (inclusive baseadas na distribuição Apache Bigtop [49]) que preferirem, além de expandir e aumentar a adoção do Hadoop em implementações em toda a corporação.

    No ambiente Big Data CAIXA, todo storage HDFS do ambiente se baseia em Dell EMC Isilon. O storage HDFS é utilizado para todo processamento distribuído no ambiente Hadoop, sejam processos Map Reduce, Apache Pig, Apache Spark ou Pivotal HDB HAWQ.

    Todos os dados do ambiente Big Data e do Data Lake estão armazenados no HDFS.

    Hadoop

    O Hadoop é uma estrutura de código e protocolo abertos, composta de vários componentes, uma biblioteca de software versátil e acessível, utilizados para o armazenamento e processamento de grandes volumes de dados.

    Apresenta estrutura escalável que admite utilização de hardware commodity de baixo custo e heterogêneo: “construa seu cluster com qualquer máquina a disposição no mercado, mesmo que todas diferentes e baratas”.

    Deste modo, apresenta baixo custo inicial e pode ser escalado conforme a necessidade.

    No ambiente Big Data CAIXA, o Hadoop provê ferramentas de:

    • Ingestão de streaming de dados (Apache Flume);

    • Processamento distribuídos de arquivos de carga batch (Apache Pig);

    • Gestão de carga/processamento distribuído (Apache Yarn);

    • Serviço de localização de serviços/servidores distribuídos (Apache Zookeeper);

    • Gestão de todas as ferramentas do ambiente (Apache Ambari);

    • Storage distribuído, tolerante a falhas e de alto desempenho (HDFS);

    • Banco de dados do Data Lake CAIXA (Pivotal HDB HAWQ).

    Pivotal HDB HAWQ

    O Pivotal HDB HAWQ é uma interface para Hadoop, que permite a realização de rápidas operações SQL sobre um grande volume de dados. A principal característica é a utilização de Massive Parallel Processing (MPP), no qual os dados são particionados em múltiplos servidores (segment servers) e cada um gerencia uma parte distinta do conjunto total de dados.

    Apresenta sintaxe de comandos SQL semelhantes ao PostgreSQL versão 8.5, pois utiliza o processador de comandos dessa versão do PostgreSQL. Entretanto, HAWQ não é um banco de dados relacional nem é compatível com a especificação de padrão SQL. É um banco de dados pseudo relacional, com estrutura tabular, sem funcionalidade para operações DELETE, sem funcionalidade para operações UPDATE, sem funcionalidade de índices (table scan) e sem funcionalidade para integridade referencial.

    Documentação dos comandos e dos comportamentos esperados está disponível nos manuais do produto em [12] [13] (PIVOTAL SOFTWARE, INC. Pivotal HDB 2.3.0 Documentation, 2018).

    Os dados disponíveis no banco de dados Pivotal HDB HAWQ do ambiente Big Data formam o Data Lake CAIXA.

    SIGPD - Sistema Gestor de Proteção de Dados

    O objetivo do sistema é atender à Lei Geral de Proteção de Dados Pessoais (LGPD ou LGPDP) [50] e ao MN CR 439 (Atendimento aos Direitos do Titular - Lei Geral de Proteção a Dados Pessoais (LGPD)) [51].

    Conforme solicitado na Avaliação/Revisão de Arquitetura 16096644 [52]: Regulatório LGPD - Relatório Técnico SIGPD – SIAPD:

    “A Lei Geral de Proteção de Dados Pessoais (LGPD ou LGPDP) disciplina os tratamentos de dados classificados como pessoais (isto é, relacionados a uma pessoa natural identificada ou identificável, inclusive menores de idade). Nesse escopo, existem dados considerados sensíveis, isto é, dados sobre origem racial ou étnica, convicção religiosa, opinião política, filiação a sindicato ou a organização de caráter religioso, filosófico ou político, dado referente à saúde ou à vida sexual, dado genético ou biométrico.

    “A LGPD define tratamento como qualquer operação realizada sobre dados pessoais (como acesso, recepção, processamento, armazenamento, expurgo, distribuição e etc.). Nesse contexto, a Lei obriga, dentre outros aspectos, a definição de que qualquer tratamento deve ter uma finalidade específica, e ser enquadrado em pelo menos uma das nove hipóteses legais, previstas na versão atual da Lei.

    “Dentre as hipóteses legais consta o consentimento, isto é, a anuência clara e incontestável da pessoa (o que requer a interação com usuário) para que tratamentos de seus dados pessoais, para aquela finalidade específica, possam ser realizados.

    “Por exemplo, para a finalidade ‘inclusão de cadastro’ no processo de digital onboarding, os tratamentos com essa finalidade provavelmente se enquadrarão na hipótese legal ‘consentimento’.

    “Na jornada dos dados de uma pessoa (nesse caso, denominada pela Lei de titular) na Caixa Econômica Federal, todos os grupos de tratamentos (sobre dados pessoais) com a mesma finalidade devem ser registrados, com controle de chancela de origem da solicitação/autorização, para fins de auditoria e apresentação de extrato de dados detalhado, que deve informar ao titular quais tratamentos foram aplicados aos seus dados.

    “Na ausência de detalhamento na LGPD e inexistência da Autoridade Nacional de Proteção de Dados (ANPD), órgão regulador do tema e que ainda não encontra-se em funcionamento, os controles, neste momento, serão bastante abrangentes, com alto grau de granularidade.

    “A ANPD poderá realizar operações de bloqueio por tempo determinado (temporário) sobre dados de determinados titulares, como uma das sanções previstas na Lei em caso de descumprimento. Na ausência de definição mais detalhada, devemos assumir que o bloqueio pode envolver: bloqueio de acesso a dado de um titular ou aos dados de grupos de titulares e, até mesmo o bloqueio de tratamentos realizados com uma finalidade específica, ou ainda, os tratamentos enquadrados em uma hipótese legal específica.

    “Desta forma, os sistemas transacionais deverão analisar todas as situações necessárias, isto é, situações em que dados pessoais sejam tratados, que, por requisitos da LGPD, devem ser enquadrados em hipóteses legais. Nestas situações, deverão verificar autorização (incluindo existência de bloqueios) para tratamentos de quaisquer dados pessoais.

    “O gestor do sistema será a DECOR, visto que o GT PRESI LGPD não possui CPNJ e tem caráter temporário.

    “Acessos:

    • A pessoa (titular, procurador, responsável legal, etc.) deve ter acesso a extrato de dados e possibilidade de alterar consentimentos relacionado aos seus dados.

    • O encarregado (Data Protection Officer) [53] deve ser capaz de acompanhar todos os extratos de dados e de realizar auditoria de autorizações.

    • Sistemas (business-to-business) devem ser capazes de verificar autorização para utilização dos dados.

    “Demanda regulatória externa. A LGPD entra em vigor em agosto de 2020.

    “Solicitamos emitir parecer com relação ao relatório técnico (anexo 1990466) complementado com as especificações suplementares para SIAPD (anexo 1992483) e SIGPD (anexo 1992481) “

    Para esse fim, o Data Protection Officer (DPO) requer capacidade de verificação e de identificação de possíveis inconsistências entre fontes de dados pessoais na CAIXA.

    Especialmente, no atendimento ao direito de correção pelo titular de dados pessoais em que qualquer correção deve ser refletida globalmente na CAIXA (aplicativos móveis, sítios web, boletos, faturas etc.) sem apresentação de divergência quanto aos dados corrigidos sob pena de sanções pela ANPD.

    Isso representa um desafio, pois existem diversas fontes de dados pessoais na CAIXA (enumeração não exaustiva): cadastros de clientes, cadastro de empregados, cadastro do saúde caixa, cadastros de programas sociais, etc.

    A representação de pessoa é consistente entre os diversos sistemas CAIXA. Entretanto, a forma de organização das informações/dados relacionadas pode ser particular em cada sistema. A perspectiva negocial e a necessidade sistêmica informam como os dados podem estar organizados em cada sistema.
