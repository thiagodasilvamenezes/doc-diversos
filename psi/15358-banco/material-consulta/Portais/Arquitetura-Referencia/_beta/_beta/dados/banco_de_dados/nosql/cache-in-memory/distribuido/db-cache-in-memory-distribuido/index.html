    Cache distribuído - SIMTX (Pagamento de Boleto)

    Arquitetura de referência de uso restrito

    Importante: Essa arquitetura de referência se encontra em fase de validação e não possui nenhum indicativo de uso geral pelas equipes. Havendo entendimento que ela se encaixa nas necessidades de seu sistema, a SUART deve ser acionada.

    A arquitetura de cache do SIMTX é Distributed Cache:

    • Os nós não serão réplicas idênticas.

    • Os dados estarão disponíveis somente em uma parcela das instâncias.

      • Visto que há necessidade de cache com volume de dados superior a quantidade possível para um único nó de processamento (os objetos precisam ser "espalhados" pelo cluster).

    • Além disso, característica da arquitetura do SIMTX indica necessidade de construção de estrutura de cache horizontal maior (várias outros processos SIMTX) que não é possível com arquitetura Replicated Cache.

    • Deve-se atentar que os dados estarão disponíveis somente em uma parcela dos servidores. Essa parcela representa o grau de durabilidade da informação.

      • Quantidade mínima de 3 instâncias para garantir durabilidade.

      • Com quantidade mínima de 2 cópias de dados devido a possibilidade de fallback.

      • Todas essas quantidades podem e devem ser maiores caso o cache seja a única fonte de dados.

    No SIMTX, o case analisado e implantado foi arquitetura de cache para processamento de Pagamento de Boleto.

    No contexto do SIMTX, todos os processos são organizados em transações. Cada transação atua em protocolo stateless [1], sem armazenar informações de quaisquer outras operações, contendo somente chaves para acesso das informações necessárias as transações no SIMTX.

    Num exemplo resumido com Caixa TEM:

    1. Transação Consultar Boleto

      1. Caixa TEM solicita ao SIMTX a transação Consultar Boleto;

      2. SIMTX realiza ação Consultar do Boleto na Câmara Interbancária de Pagamentos (CIP) [2];

      3. SIMTX armazena, na camada de persistência, as informações do boleto;

      4. SIMTX retorna a informação do Boleto e identificador CHAVE_NSU_CONSULTA_BOLETO para o CAIXA TEM.

    2. Transação Validar Boleto (Caixa TEM não tem as informações consultadas anteriormente, somente CHAVE_NSU_CONSULTA_BOLETO para consulta das informações do boleto armazenadas na Transação Consultar Boleto)

      1. Caixa TEM solicita ao SIMTX a transação Validar Boleto informando a CHAVE_NSU_CONSULTA_BOLETO para consulta das informações do boleto;

      2. SIMTX consulta, na camada de persistência, os dados do boleto anteriormente obtidos na Transação Consulta Boleto.

      3. SIMTX realiza ação Validar Boleto;

      4. SIMTX armazena, na camada de persistência, as informações de resultado da ação Validar Boleto;

      5. SIMTX retorna as informações resultantes apropriadas e identificador CHAVE_NSU_VALIDA_BOLETO para Caixa TEM.

    3. Transação Pagar Boleto (Caixa TEM não tem as informações de resultado da ação Validar Boleto anterior, somente CHAVE_NSU_VALIDA_BOLETO para consulta das informações do boleto armazenadas na Transação Consultar Boleto)

      1. Caixa TEM solicita ao SIMTX a transação Pagar Boleto informando a CHAVE_NSU_VALIDA_BOLETO para consulta das informações de validação do boleto;

      2. SIMTX consulta, na camada de persistência, os dados de validação do boleto anteriormente obtidos na Transação Valida Boleto.

      3. SIMTX realiza ação Pagar Boleto;

      4. SIMTX armazena, na camada de persistência, o identificador do código de barras do boleto pago;

      5. SIMTX retorna as informações resultantes apropriadas para Caixa TEM.

    1. Os dados armazenados em cache ao final da Transação Consultar Boleto serão lidos no início da Transação Validar Boleto utilizando como chave NSU1 da Transação Consultar Boleto;

    2. Os dados armazenados em cache ao final da Transação Validar Boleto serão lidos no início da Transação Pagar (ou, Agendar) Boleto utilizando como chave NSU da Transação Validar Boleto;

    3. Na Transação Pagar Boleto serão gravadas no banco de dados todas as informações de boleto necessárias para processamentos posteriores, como por exemplo, para emissão de comprovantes. Entretanto, no cache será gravado apenas a chave de consulta, que é o código de barras dos boletos efetivamente pagos. Essa lista de códigos de barras em cache será consultada no início da Transação Consultar Boleto e Transação Validar Boleto.

    Todas as informações armazenadas são consecutivamente e estaticamente (sem alterações) consultadas. Para continuidade das transações seguintes, que também armazenam seus resultados. De forma recorrente.

    Percebe-se um sequenciamento de operações em um processo de workflow [3]. Em que a aplicação realiza escrita de informação com sequencial leitura dessa mesma sem qualquer alteração.

    Que podem apresentar uso significativo da camada de persistência de banco de dados transacional do SIMTX.

    O cenário atende aos critérios identificados para uso de cache:

    • Existe informação que pode ser reaproveitada: informações "trafegadas" entre Consultar Boleto, Validar Boleto e Pagar Boleto. Entretanto, as informações armazenadas de modo geral serão recuperadas somente uma vez. Não obstante, todos os processos do SIMTX apresentam esse comportamento de informações anteriores necessários para as próximas transações desse processo;
    • Existe potencial custo elevado: acesso constante à camada de persistência com escrita e leituras sequenciais a cada etapa do processo de Pagamento de Boleto devido ao protocolo stateless adotado. O custo deve ser analisado visto que todos os processos do SIMTX apresentam esse comportamento;

    • O resultado não se altera para operações subsequentes: informações armazenas para Consultar Boleto, Validar Boleto e Pagar Boleto armazenadas podem ser reaproveitadas por até N segundos/minutos/horas/etc;

    • Em situações em que o custo da operação f(x) justifique a estrutura e em que a redução do custo apresenta resultado significativo: área responsável por infraestrutura de banco de dados identificou alto consumo de recursos de banco de dados da aplicação com operações que não requerem processamento transacional posterior (após INSERT, não sofrem DELETE ou UPDATE) [4] em um processo de "escreve para logo ler novamente".

      • A utilização de cache vem atender ao crescimento de volumetria de operações no SIMTX com a expansão do portfólio dos serviços prestados por esse; além da migração projetada de operações de outros sistema para o SIMTX. Além disso, a arquitetura de cache para o processo de boleto do SIMTX pode se expandir para os demais processos que apresentam o mesmo cenário.

        • Há volume diário de 700 mil transações diárias para processamento de Pagamento de Boletos apenas para contas NSGD: sociais, poupança e conta salário.

          • Há previsão de migração de 4 milhões de contas SIDEC para NSGD com impacto direto no volume de Pagamento de Boletos.

        • Além disso, SIMTX processa transações relacionadas ao PIX que apresentou crescimento de 2 milhões de transações no período de 1 ano.

    Desta forma, as informações necessárias para execução de transações subsequentes no processo de Pagamento de Boleto serão armazenadas em cache pelo período de tempo N (segundos/minutos/horas/etc).

    • Haverá redução nos acessos de leitura ao banco de dados.

      • Reduzindo o impacto do protocolo stateless na infraestrutura.

        • Reduzindo a carga concorrente das escritas de informações transacionais com as leituras de dados inalterados.

      • Especialmente considerando-se a expectativa de expansão e crescimento do SIMTX.

    • O tempo de vida N da informação no cache deve ser definido negocialmente.

      • Por exemplo, pode ser definido tempo N padrão por tipo de informação armazenada no cache.

        • Ou, um tempo N diferente para cada informação recuperada independentemente do tipo.

      • O tempo N deve ser o maior possível negocialmente de modo a maximizar o comportamento desejado do cache.

      • Segundo definição da equipe da comunidade do SIMTX, os tempos de vida N definidos são:

        • 2 minutos para Transação Consultar Boleto e Transação Validar Boleto;

        • 15 minutos para Transação Pagar Boleto.

    Um cache compartilhado de dados reduziria tanto o volume quanto a frequência de acesso por essas informações repetidas.

    Análise do processo de Pagamento de Boleto

    No SIMTX, identificamos os seguintes 3 cenários para utilização de estrutura de cache para troca de informações entre as transações do processo de pagamento de boleto:

    1. Consultar Boleto

    2. Validar Boleto

    3. Pagar Boleto

    Transação Consultar Boleto (fragmento incluindo somente essa transação)

    Características de Transação Consultar Boleto:

    Características
    Payload (bytes) 2.112
    Tempo de vida (segundos) 120
    Tolerância a cache MISS Sim
    Fallback em cache MISS Banco de dados
    Volume diário de objetos escritos em cache 500.000
    Volume diário de objetos escritos em cache em período de pico 970.000
    Volume de acessos simultâneos ao cache em um intervalo de 5 minutos em período de pico 14.000
    Volume de acessos simultâneos para escrita ao cache em um intervalo de 5 minutos em período de pico 7.000
    Volume de acessos simultâneos para leitura ao cache em um intervalo de 5 minutos em período de pico 7.000
    Objetos simultâneos em cache 1.000
    Tempo de resposta (entre escrita e disponibilidade para leitura) (segundos) 4

    • Payload: 3 kibibytes em formato texto JSON.

      • Key: Chave será o NSU criado no processo de consulta (diferente do NSU do processo de validação): formato numérico com comprimento de 15 caracteres (bytes).

      • Value: Tamanho máximo de 2.097 caracteres (bytes) incluindo todos os caracteres separadores JSON.

    • Time to Live: objetos podem ser removidos após 120 segundos.

    • Existe tolerância de cache MISS, mesmo que indesejável.

      • Cache MISS com fallback para consulta ao banco de dados.

      • Cache não precisa ser persistente (as informações não precisam ser armazenadas em banco de dados).

    • Volume diário de 500 mil objetos gravados no cache.

      • Com pico de 970 mil objetos ao longo do mês (Volume observado em 09/01/2023).

    • Volume de acessos simultâneos.

      • Volume aproximado de 14.000 acessos a cada 5 minutos no horário de maior movimento.

      • 7000 acessos para leitura e 7.000 acessos para escrita.

      • Pico de aproximadamente 1.000 objetos simultâneos no cache.

    • Tempo de resposta

      • Objetos devem estar disponível ("prontos") para leitura em tempo inferior a 4 segundos após gravação no cache.

        • Desejável em tempo inferior a 2 segundos.

    Transação Pagar Boleto (fragmento incluindo somente essa transação)

    Características de Transação Pagar Boleto:

    Tabela - Características da Transação Pagar Boleto

    Características
    Payload (bytes) 44
    Tempo de vida (segundos) 900
    Tolerância a cache MISS Não
    Fallback em cache MISS Não há. Aplicação prosseguirá sem a informação
    Volume diário de objetos escritos em cache 500.000
    Volume diário de objetos escritos em cache em período de pico 970.000
    Volume de acessos simultâneos ao cache em um intervalo de 5 minutos em período de pico 21.000
    Volume de acessos simultâneos para escrita ao cache em um intervalo de 5 minutos em período de pico 14.000
    Volume de acessos simultâneos para leitura ao cache em um intervalo de 5 minutos em período de pico 7.000
    Objetos simultâneos em cache 1.000
    Tempo de resposta (entre escrita e disponibilidade para leitura) (segundos) 4

    • Payload:

      • Key: Chave será o identificador do código de barras do boleto (diferente do NSU do processo de consulta/validação): formato alfanumérico com comprimento de 44 caracteres (bytes).

      • Value: não serão armazenados objetos no cache.

      • O cache será utilizado como uma skip list (teste de existência no cache) flat simplificada.

    • Time to Live: objetos podem ser removidos após 15 minutos

    • Não existe tolerância de cache MISS.

      • Cache MISS com fallback para consulta ao banco de dados.

      • Cache não precisa ser persistente (as informações não precisam ser armazenadas em banco de dados).

      • Entretanto, cache para Transação Pagar Boleto não admite cache MISS para objetos que não teriam ultrapassado o TTL de 15 minutos.

        • Não há risco de perda, pois as informações da Transação Pagar Boleto são sempre armazenadas no banco de dados exatamente como as demais transações.

      • Entretanto, dentro dos 15 minutos em que o pagamento boleto pode não ter sido ainda enviado para a CIP, o SIMTX poderá realizar pagamento de boleto em duplicidade se não encontrá-lo no cache.

    • Volume diário de 500 mil objetos gravados no cache.

      • Com pico de 970 mil objetos ao longo do mês (Volume observado em 09/01/2023).

    • Volume de acessos simultâneos

      • Volume aproximado de 21.000 acessos a cada 5 minutos no horário de maior movimento.

      • 7000 acessos para leitura e 14.000 acessos para escrita.

      • Pico de aproximadamente 1.000 de objetos simultâneos no cache.

    • Tempo de resposta

      • Objetos devem estar disponível ("prontos") para leitura em tempo inferior a 2 segundos após gravação no cache.

        • Desejável em tempo inferior a 1 segundo.

    Características do cache

    Recomendamos construção de ambiente com OKD 3.11 e Red Hat Data Grid 8.1.

    • Em vista da criticidade: necessidade de implantação imediata da solução em produção;

      • Apesar da recomendação do fornecedor, o OKD 4 ainda se encontra em fase de implantação.

      • Há ampla disponibilidade de OKD 3.11 no ambiente CAIXA.

    Não obstante, deve-se explorar utilização futura de OKD 4 considerando as vantagens identificadas pelo fornecedor.

    O cenário de cache do SIMTX se apresenta diferente ao do SISPI:

    • Há necessidade de 3 caches diferentes para atender seu fluxo de transações devido as diferenças de comportamento (workloads) entre as transações,

      • Em contraste ao cache único do SISPI para o processo DICT BACEN.

    • A arquitetura de cache do SIMTX é Distributed Cache , pois há necessidade de cache com volume de dados superior a quantidade possível para um único nó de processamento (os objetos precisam ser "espalhados" pelo cluster).

      • Arquitetura em cluster aumenta a disponibilidade e capacidade de processamento/armazenamento.

    3 caches, um por tipo de Transação (Consultar/Validar/Pagar Boleto) com as seguintes características comuns de configuração da ferramenta:

    Tabela - Características comuns dos caches para o processo Pagamento de Boleto.

    Cache
    Ferramenta Red Hat Data Grid
    Clustered Mode Distributed cache
    Nodes Quantidade dependente dos critérios de replicação e quantidade de objetos
    Owners 2
    Replication Síncrona (blocante) para escrita inicial e assíncrona nas réplicas
    Transaction Write lock
    Política de exclusão automática Time aware least recently used

    • Ferramenta: Red Hat Data Grid

    • Cliente Data Grid: somente pode ser desenvolvido em Java framework Quarkus com protocolo Hot Rod.

      • Configurações alternativas apresentaram desempenhos 10 vezes a 100 vezes inferiores em testes de stress.

    • Clustered Mode: Distributed Cache

      • Os objetos não estão replicados em todos os nós do cluster.

      • Arquitetura em cluster aumenta a disponibilidade e capacidade de processamento/armazenamento.

    • Nodes: quantidade será definida pela memória requerida para o cluster.

      • Quantidade de servidores no cache distribuído.

    • Owners: 2

      • Quantidade de cópias/réplicas de um objeto no cache distribuído.

      • Representa o grau de tolerância a falhas.

    • Replication: síncrona com replicação assíncrona

      • Serviço do cache somente informa sucesso na escrita de objetos quando ocorrer a escrita síncrona no nó do cache que foi acessado.

      • Entretanto, serão criadas no mínimo NUMERO_OWNERS réplicas de forma assíncrona. Ou seja, no mínimo 2 réplicas.

    • Transaction: Write lock

      • Serviço do cache garante que somente uma operação de escrita ocorre por vez para uma key (chave), ou seja, lock de escrita.

    • Política de exclusão automática: time aware least recently used (TLRU) [5]

      • Exclusão automática de mensagens que ultrapassarem TTL de N minutos.

        • No qual N é no mínimo:

          • 2 minutos para Transação Consultar Boleto e Transação Validar Boleto;

          • 15 minutos para Transação Pagar Boleto.

      • Recomendado TLRU ou similar para tratamento de evento de cache "cheio".

      • 3 gibibytes na mesma configuração do SISPI.

      • De acordo com documentação do Red Hat Data Grid 8.4, JVM Heap deve ser configurado para ao menos o dobro do espaço requerido para os objetos do cache.

        • Logo, 1.500 mebibytes seria o tamanho máximo para armazenamento de objetos no cache por nó.

        • Entretanto, será ajustado para 1.250 mebibytes de tamanho máximo de armazenamento de objetos.

          • Desse modo, cada nó apresentará 512 mebibytes para uso interno do nó: overhead de JVM, memória alocada para shell script, etc.

          • O JVM Heap deverá ser configurado para ao menos 2.500 mebibytes.

    • Payload (objeto para cache)

      • É calculado com composição (soma) do tamanho da chave (key) e do valor (value).

        • Deve ser calculado payload médio detectado no ambiente real proposto.

          • Caso contrário, o tamanho máximo possível.

        • Além da adição de overhead de 200 bytes por objeto (métrica do Red Hat Data Grid) em JVM Heap ou overhead de 60 bytes por objeto em memória "off-heap". Esses são valores aproximados de overhead. Valores precisos exigem análise de heap dumps em cada projeto específico.

      • Tamanho da chave em bytes MAIS tamanho do valor em bytes MAIS 200 bytes.

      • Para estimativa da memória necessária e consequentemente da quantidade de nós necessários para o cluster, primeiro identificaremos quantos objetos simultâneos deverão estar disponíveis na memória.

      • Na ausência de quantidade negocial específica, utilizaremos a quantidade de objetos no pico de processamento.

    • Depois, analisaremos o tempo de vida dos objetos. Quanto objetos simultâneos deverão estar armazenados no cache, e por quanto tempo, para identificarmos a capacidade (profundidade).

      • Por exemplo, para Transação Consultar Boleto: TLL de 120 segundos com 1.000 objetos simultâneos resulta em capacidade de 120.000 objetos.

    • Consequentemente, podemos calcular o tamanho do cache mínimo necessário para armazenar essa quantidade de objetos. Ou seja, a memória necessária para armazenar uma cópia completa do cache. Iremos identificar esse valor como "data set size" para manter o padrão de nomenclatura da documentação oficial do produto.

    • A memória necessária, para execução simultânea dos 3 caches (752 mebibytes), é inferior a memória disponível por nó de 1.250 mebibytes para armazenamento de objetos.

      • A memória necessária para execução de qualquer um dos caches é inferior a memória disponível por nó.

        • Deve-se investigar redimensionamento dos nós.

    • Tanto o tempo de vida quanto a quantidade de objetos simultâneos devem ser identificados de modo apropriado pela equipe de projeto visto o impacto direto na infraestrutura necessário e no desempenho da arquitetura de cache.

    • Número mínimo de nós para cluster Data Grid

      • Conforme documentação "Red Hat Data Grid 8.4 - Data Grid Performance and Sizing Guide, 2023", o número mínimo de nós para cada cache é dependente:

        • Do tamanho total de cache calculado acima (data set size);

        • Do número de réplicas mínimas para cada objeto (owners definidos como 2 para esse case);

        • Da memória disponível por nó para armazenamento de objetos (definidos como 1.250 mebibytes para esse case).

      • Para o case do SIMTX, são necessários no mínimo 2 nós por tipo de cache para garantir 2 réplicas (2 owners) para cada objeto.

        • O cálculo não seria necessário para a memória definida de 1.250 mebibytes por nó, visto que o tamanho total do cache é inferior ao espaço disponível em cada nó.
