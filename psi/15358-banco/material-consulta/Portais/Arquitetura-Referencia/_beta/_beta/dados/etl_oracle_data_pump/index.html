    Extract-Transform-Load (ETL)

    Análise de Solução

    Processos de integração representam uma ou mais entidades cooperando e/ou interagindo para alcançar algum objetivo.

    Dentre esses processos, existem classes de problemas de cooperação que ocorrem por meio de troca de informações entre entidades; i.e., integração de dados [1].

    Integração de dados pode ser definida como um problema de mapeamento de grupos:

    • Uma função de mapeamento t1 (transformação) que mapeia todo o conjunto o1 (origem) para o conjunto d1 (destino).

    • Generalizado como um conjunto de funções de mapeamento T (transformações) que mapeiam todo grupo O de fontes de dados para todo grupo D de destinos de dados.

    Que também são conhecidos como classes de problemas de Extract-Transform-Load (ETL) [2] [3] [4], resumidamente:

    • Extract: coleta de dados a partir de uma ou mais fontes de dados (O);

    • Transform: conjunto de funções (T) aplicada aos dados coletados que podem incluir, mas não estão limitados a reorganização, transformação, análise, enriquecimento, etc.

    • Load: disponibilização de dados em um ou mais destinos de dados (D).

    Existindo variações:

    • E-L : processos de extract e de load, mas sem processos de transformação; para cenários de replicação entre fontes de dados e destinos de dados.

    • ELT : extract, load then transform; separando o processo e/ou a ferramenta de transformação dos processos de extract e de load.

      • Extract: Coleta de dados a partir de uma ou mais fontes de dados (O);

      • Load: disponibilização de dados em uma plataforma de dados como destino de dados (D).

      • Transform: utilizando a plataforma de dados de destino, aplica conjunto de funções (T) aplicada aos dados coletados.

    A variação ELT em particular se destaca por essa separação entre os processos Extract-Load e Transform; tanto entre ferramentas quanto por estratégia.

    • O objetivo principal é transportar os dados das origens de dados para os destinos de dados.

    • A transformação somente ocorrerá em uma fase posterior e separada de todo processo de extract e de load.

      • Toda transformação se valerá da infraestrutura e do ferramental do destino ao invés das ferramentas do pipeline Extract-Load.

        • Estratégia que se popularizou com a disponibilidade de ferramentas de Big Data que apresentam alta escalabilidade [5], bem como a escalabilidade de infraestruturas em cenários de nuvem;

        • Tornando vantajoso realizar replicação para essas estruturas escaláveis e somente realizar o processamento a posteriori.

      • Outra razão, é garantir a existência das réplicas de dados.

        • Réplicas das origens de dados devem estar disponíveis para processos de analytics;

        • Quaisquer transformações podem ocorrer e ser disponibilizadas, mas não podem interferir nem alterar as réplicas das origens de dados.

    Ademais, devemos nos atentar que um ciclo ETL completo não se limita aos 3 passos acima. Trata-se de um conjunto de processos que garantem controle, qualidade e gestão em um processo global de ETL.

    • Cycle initiation

    • Build reference data

    • Extract (from data sources)

    • Validate

    • Transform (clean, apply business rules, check for data integrity, create aggregates or disaggregates)

    • Stage (load into staging structures, if used)

    • Audit reports (for example, on compliance with business rules. Also, in case of failure, helps to diagnose/repair)

    • Publish (to data targets)

    • Archive

    Arquitetura implantada (ATUAL)

    Os processos de integração de dados ETL envolvem as mais diversas origens de dados e os mais diversos destinos de dados, que podem ser:

    • Arquivos: flat file [6] binários/textos com ou sem separadores; ou, mais complexos como Apache ORC [7], Apache Parquet [8], IBM Virtual Storage Access Method (VSAM) [9], etc;

    • Sistemas Gerenciadores de Bancos de Dados (SGBD) [10]: IBM Db2 [11] for z/OS [12], Oracle Exadata [13]/RAC [14]/stand alone [15], Microsoft SQL Server [16], SAP ASE [17], SAP IQ [18], etc;

    • Eventos: API [19], IBM MQ [20], etc;

    • Formatos: estruturados, semiestruturados [21], não estruturados [22], etc;

    • Modelos de bancos de dados [23]: dimensional, multidimensional, documento, grafo, hierárquico, rede, relacional, não-relacionais, etc.

    Envolvendo diversas funções de transformação. Por exemplo:

    • Conversão de campos negocialmente "vazios" (valor zero 00000) para tecnologicamente "vazios" (tipo null);

    • Remoção de caracteres invisíveis;

    • Remoção de caracteres inválidos;

    • Conversão entre tipos de codificação de caracteres [24] diferentes; e.g., entre EBCDIC e UTF-8;

    • Conversão entre tecnologias.

      • Por exemplo, de arquivo VSAM sequencial EBCDIC em arquitetura z [25] IBM mainframe [26] para banco de dados Oracle Exadata com codificação UTF-8 em arquitetura X86/X64.

    As origens de dados e os destinos de dados mais comuns são:

    • Arquivos

    • Bancos de dados relacionais

    Opções para alvos transacionais (destinos de dados)

    É possível realizar processos Load de alto desempenho com modo bulk loading - (Informatica PowerCenter 10.5 - Workflow Basics Guide).

    • Carga em blocos para bancos de dados Db2, Microsoft SQL Server, Oracle e Sybase;

    • Entretanto, modo de bulk loading também inativa logging tornando irreversível as operações;

      • Caso logging esteja ativo, todas as operações serão armazenadas nesse, de modo a permitir operação de rollback.

      • Caso não esteja ativo, não será possível reverter as operações, mas haverá ganho de desempenho na execução dessas.

    • Com relação a commit:

      • Para destinos de dados Db2 e Sybase, commits ocorrem quando writer block estiver cheio, independente da configuração da sessão.

      • Para destinos Microsoft SQL Server e Oracle, o intervalo de commit definido na sessão é respeitado.

        • Além disso, uma nova transação bulk load é criada após cada commit.

        • Recomenda-se definir um intervalo longo (maior) entre commits para aumento de desempenho.

    Operações DML (insert/delete/update) podem ser realizadas com logging ativo ou inativo.

    Deve-se notar que é possível realizar Load que respeite as constraints referenciais (constrainst-based loading ) da origem de dados: as tabelas pais dos relacionamento são carregadas antes das tabelas filhas. Entretanto, essa funcionalidade restringe o processo de carga para processamento linha (row) a linha ao invés de processo em bloco (bulk).

    Constrainst-based loading permite um modo seguro e íntegro para processos de carga. Entretanto, apresenta impacto no desempenho.

    Arquitetura definida (FUTURA)

    Oracle

    Adicionalmente, para novos cenários Oracle, pode-se analisar a utilização de utilitário Data Pump [34] para movimentação de dados, sem transformação, entre tabelas de mesma estrutura em instâncias diferentes, em que a origem de dados é uma partição.

    Na arquitetura proposta, o Data Pump será utilizado para propagação de dados em estrutura de bases de dados do Oracle, divididos em 4 passos:

    • Geração do arquivo de dump através do comando expdp.

    • Carga do arquivo de dump no destino, através do impdp.

    • Drop/truncate da partição na origem.

    • Exclusão do arquivo utilizado para carga.

    O Data Pump é composto de três partes distintas.

    • Utilitários de linha de comando.

      • expdp : Executa a exportação dos dados para arquivos.

      • impdp: Executa a importação dos dados para o banco de dados.

    • Pacote PL/SQL DBMS_DATA PUMP

      • É responsável por prover todas as informações necessárias para execução do utilitário, suportando desde as conexões de origem e destino até o nome dos objetos manipulados.

    • Pacote PL/SQL DBMS_METADATA.

      • É responsável recuperar os metadados dos objetos armazenados no catalogo do banco de dados.

      • É utilizada por todos os processos de carga e descarga dos metadados.

    Não deve ser utilizado export "using SYS as SYDBA". A permissão SYSDBA é usada internamente e tem funcionalidades especializadas; não se comportando como um usuário genérico.

    A utilização do parâmetro parfile (arquivo com os parâmetros separados) deve ser priorizada, pois limita o número de informações na linha de comando. O arquivo fornecerá os parâmetros para execução do utilitário, tornando o processo mais seguro, ágil e de fácil leitura dos critérios executados.

    Exemplo sem parfile:

    expdp hr/hr@oracle directory=dir1 dumpfile=dump.dmp tables=Empregado,departamento

    Exemplo com parfile:

    expdp hr/hr@oracle parfile=exp.par
    • Arquivo "exp.par":

    +-----------------------------------------------------------------------+
| directory=dir1                                                        |
|                                                                       |
| dumpfile=dump.dmp                                                     |
|                                                                       |
| Tables=Empregado,departamento                                         |
+=======================================================================+
+-----------------------------------------------------------------------+
    O Data Pump deve ser utilizado somente com PARTITION no modo TABLE.

    +-----------------------------------------------------------------------+
| expdp DB_USER/DB_PWD directory=DIR_DUMP dumpfile=dumpfile.dmp \\      |
|                                                                       |
| logfile=logfile.log tables=TABELA:PARTICAO EXCLUDE=STATISTICS         |
| METRICS=YES                                                           |
+=======================================================================+
+-----------------------------------------------------------------------+

+-----------------------------------------------------------------------+
| impdp DB_USER/DB_PWD directory=DIR_DUMP dumpfile=dumpfile.dmp \\      |
|                                                                       |
| logfile=logfile.log tables=TABELA:PARTICAO EXCLUDE=STATISTICS         |
| METRICS=YES                                                           |
+=======================================================================+
+-----------------------------------------------------------------------+

    Por recomendação da Oracle, as estatísticas não devem ser exportadas durante o processo de export e de import. Isso irá garantir melhor performance na execução dos utilitários. A melhor prática deve ser a criação de novas estatísticas no database de destino utilizando o package DBMS_STATS.

    Os parâmetros de diagnóstico devem ser incluídos durante o export e o import. Para tanto, deve ser utilizado o parâmetro METRICS=YES, que traz um nível extra de detalhamento do trabalho executado pelo utilitário.

    Fonte -- Oracle \[35\] (ORACLE; , A. Oracle Database Utilities - Oracle Data Pump Best Practices, ago. 2021)

    O paralelismo traz um ganho de performance para o utilitário Data Pump. O parâmetro PARALLEL=n especifica o número máximo de processos executados durante um export ou import. O valor de n recomendado é o dobro do número de cores CPU, mas pode ser ajustado de forma a melhorar a performance. O número n adequado deve ser avaliado em conjunto com os DBAs visto sua administração da infraestrutura de servidores Oracle.

    Com o paralelismo, é possível criar máscaras para a criação dos arquivos de dump, utilizando as variáveis de substituição %U ou %L na definição do nome de arquivo. Ainda, múltiplos arquivos de dump de menor tamanho facilitam a administração e a cópia.

    Após a carga com sucesso, o(s) arquivo(s) de carga .dmp devem ser removidos.

    Critérios

    A arquitetura de replicação por utilitário Oracle Data Pump busca incremento de desempenho, pela condição nativa da solução.

    Dessa forma, propomos os seguintes critérios para identificação de processos candidatos ao uso dessa arquitetura:

    • As rotinas devem ser compatíveis e utilizadas em conjunto com a ferramenta BMC Control-M [36].

      • O controle de fluxo de execução deve ser realizado pela aplicação.

      • O drop/truncate da partição só poderá ocorrer após a importação > do dado no database/objeto de destino com sinalização de > sucesso para o Control-M.

    • Deverá ocorrer apenas movimentação de dados entre um objeto Origem e um Objeto Destino, sem transformação de dados.

    • O objeto de destino deve conter a mesma estrutura da tabela de origem.

    • O charset do database de destino preferencialmente deve ser um superset do database de origem.

      • De forma que o destino contenha todos os caracteres da origem.

      • Há risco de perda de dados, caso os charsets sejam diferentes/incompatíveis.

    • Deve gerar log de saída com as seguintes informações:

      • Usuário que executou a operação

      • Nome do script executado

      • echo (imprimir) do comando que será executado.

      • Nome da [instancia].[schema].[objeto] manipulado

        • Quantidade de linhas previstas

        • Quantidade de linhas manipuladas

      • Hora de início e fim do processamento

      • Erros ocorridos durante a execução (códigos e mensagens de erro da ferramenta ETL)

    Tecnologia

    Oracle Data Pump

    O Oracle Data Pump é um utilitário, disponível no SGBD Oracle, utilizado para atividades de exportação e importação de dados de forma nativa.

    Deve-se observar que o utilitário não é uma ferramenta de ETL completa;

    • Trata-se de ferramenta E-L com processos de extract e de load;

    • Não é possível realizar transformações. Por exemplo

      • Conversões adicionais de codificação de caracteres;

      • Remoção de espaços em branco;

      • Remoção de caracteres invisíveis;

      • Conversão de 0000 (valor zero) para "null";

    • Trata-se de uma ferramenta de cópia/movimentação de dados, com alto desempenho, entre instâncias Oracle; dessa forma, não permite interoperabilidade com outras tecnologias de SGBD (por exemplo, IBM Db2 for z/OS);

    • As extrações e importações somente podem ser realizadas entre instâncias em que exista compatibilidade entre as versões dos utilitários disponíveis em cada uma das instâncias;

    O Data Pump Export (expdp) pode produzir os seguintes tipos de arquivos:

    • Dump:

      a. Arquivo binário, com formato proprietário, que armazena os dados e metadados exportados.

      b. Possui a extensão .dmp

    • Log:

      a. Arquivo de log que grava as mensagens associadas ao job em execução.

      b. Possui a extensão .log

    • SQL:

      a. Todos os comandos Data Definition Language (DDL) [37] gravados em um arquivo SQL.

      b. Possui a extensão .sql

      c. É utilizado para geração de scripts DDL e migração de bases de dados.

    Interfaces de uso: A interação com o Oracle Data Pump pode ser realizada através de linha de comando, arquivo de parâmetro ou interface interativa.

    O Data Pump possui vários modos de utilização, a depender dos tipos de objetos a serem exportados/importados.

    • FULL - Realização de um full export do database.

    • SCHEMA - É o default do Data Pump. Realiza export dos schemas informados.

    • TABLE - São exportadas apenas as tabelas indicadas.

    • TABLESPACE -- Arquivo físico que armazena um ou mais objetos.

    • TRANSPORT_TABLESPACES -- Nesse modo, apenas os metadados das tabelas (e seus objetos dependentes), dentro dos tablespaces especificados, são exportados. Os arquivos físicos dos tablespaces devem ser movidos manualmente entre os servidores.

    As opções de filtro do Data Pump permitem limitar o tipo de informação a ser exportada, através do parâmetro CONTENT.

    CONTENT -- Permite filtrar o tipo de informação em o que o export processará, da seguinte forma:

    • CONTENT = ALL. Extrai tanto os dados quanto os metadados dos objetos. É o default.

    • CONTENT = DATA_ONLY. Extrai somente os registros das tabelas; nenhuma definição de objeto é extraída.

    • CONTENT = METADATA_ONLY. Extrai apenas as definições dos objetos do database.

    Antes de iniciar um Export e/ou Import, deve-se especificar em qual diretório no servidor de banco de dados serão mantidos os arquivos de Log, Dump e/ou SQL.

    No exemplo abaixo, criamos o diretório Data_Pump_diretorio que aponta para o diretório físico /migraBR/MIGRACAOEXA, depois indicamos os acessos (grants) concedidos para ler e escrever neste diretório.

    +-----------------------------------------------------------------------+
| SQL\> CREATE DIRECTORY Data_Pump_diretorio as '/migraBR/MIGRACAOEXA'; |
|                                                                       |
| SQL\> GRANT READ, WRITE, ON DIRECTORY Data_Pump_diretorio to          |
| SPCARTB1;                                                             |
+=======================================================================+
+-----------------------------------------------------------------------+

    O usuário executor do expdp e impdp requer privilégio nas roles DATA_PUMP_EXP_FULL_DATABASE e DATA_PUMP_IMP_FULL_DATABASE. Estas roles são criadas automaticamente na instalação do Oracle, permitem que o usuário realize export e import de objetos pertencentes a outros schemas; além de permitir monitoração de processos iniciados por outros usuários.

    • DUMPFILE

      • Especifica o nome do arquivo que será gravado;

      • O arquivo possui os metadados e os dados exportados.

    • TABLES

      • Sintaxe: TABLES=[schema_name.]table_name[:partition_name]

      • Especifica que o Data Pump será realizado em modo de tabela.

      • No exemplo, foi realizado o export da partição EVENTO_SPED_1 da tabela EFI.EFITB055_EVENTO_SPED.

    • LOGFILE

      • Especifica o nome dos arquivos gerado que grava as mensagens de execução do job.

    Algumas options foram incorporadas à solução de Data Pump para incremento de desempenho e melhoria no gerenciamento:

    • PARALLEL -- Capacidade de especificar o número máximo de segmentos de execução ativos operando no Data Pump. Isso permite ajustar o consumo de recursos conforme o tempo.

    • START_JOB -- Capacidade de reiniciar o comando em caso de falha. Isso permite ao DBA e outros usuários a monitorar a execução de JOBS.

    • NETWORK_LINK -- Oferece suporte para execuções remotas, nas quais as fontes de informação são as próprias instâncias, sem a necessidade de gerar arquivo físico em disco.

    • REMAP_DATAFILE e REMAP_TABLESPACE -- a capacidade de alterar o nome dos arquivos de dados e armazenamento na origem para outro destino, no caso de replicação de um ou mais bancos de dados.

    • ESTIMATE_ONLY - permite simular o tamanho do dump (quanto ocuparia em disco, caso se optasse por essa opção) e até o tempo necessário para o processo de exportação e importação do Data Pump.

    • VERSION -- capacidade de adequação à versão que se pretende exportar/importar, utilizada para realizar o upgrade/downgrade de versões.

    • QUERY - Permite especificar uma query para filtrar os dados a serem exportados.

    +-----------------------------------------------------------------------+
| expdp hr/hr SCHEMAS=ICO QUERY=(ICO.ICOTBU24_UNIDADES:\"WHERE          |
| NU_UNIDADE = 1000") \\                                                |
|                                                                       |
| dumpfile=ico.dmp logfile=ico.log                                      |
+=======================================================================+
+-----------------------------------------------------------------------+

    Os parâmetros apresentados não cobrem todas as opções disponibilizadas pelo fabricante, dessa forma, para mais opções acesse a documentação de referência do Oracle Data Pump [34] (ORACLE. Oracle Data Pump | Oracle Database Release 21 | Database Utilities. Oracle Help Center, 2022).

    Pontos de atenção

    • Utilização de NFS traz OVERHEAD e risco com utilização de estrutura externa ao Exadata.

      • Indisponibilidades no meio intermediário de armazenamento impedirá a execução.

      • O desempenho da exportação e importação pode ser impactado em função das características do storage utilizado.

        • Bem como impactos de rede no processo: throughput, latência, tempo de resposta, etc.

    • Dificuldade na utilização de DBLINK.

      • Dificuldades de implementação de segurança e processo.

      • Impacto entre as instâncias conectadas por DBLINK.

        • Em que uma instância pode causar impacto em outra com execução remota de queries.

    • A gestão da execução do processo do Data Pump é manualmente construída.

      • A equipe de desenvolvimento deve planejar a estratégia de movimentação, considerando os relacionamentos entre as tabelas.

    • As estatísticas devem ser executadas antes e depois das operações de Data Pump.

      • Na origem de dados, antes do início do processo para aumentar a velocidade da exportação.

      • No destino de dados, depois de finalizado o processo para melhorar o desempenho das consultas.

    Case

    SISMPI (PIX)

    No SIMPI (PIX), são processados um volume superior a 15 milhões de transações PIX por dia. O banco de dados do SIMPI apresenta alto tempo de processamento devido à alta volumetria de dados em suas tabelas.

    Deste modo, há recomendação para movimentação de dados para outras tecnologias. Por exemplo, movimentação de dados históricos para Oracle standalone. Com a construção de base de dados apartada para movimentação de dados da base transacional online do sistema, buscando redução no tempo de resposta das transações e consequentemente redução de volumetria atual.

    Condições para execução do cenário

    • O objeto de destino deve conter a mesma estrutura da tabela de origem

      • Não deverá ocorrer a execução de comandos do tipo DROP/TRUNCATE > na estrutura de destino.

      • A carga de dados na estrutura de destino deverá ser no formato > APPEND.

    • Devem ser definidos os critérios da execução do Data Pump, como as partições e objetos

      • As partições podem ser identificadas por meio de query e de forma dinâmica compor o parâmetro do utilitário para execução do export/import, conforme exemplo a seguir:
    +-----------------------------------------------------------------------+
| SELECT partition_name, high_value, table_name                         |
|                                                                       |
| FROM dba_tab_partitions WHERE TABLE_owner = \'EFI\';                  |
+=======================================================================+
+-----------------------------------------------------------------------+

    • Partição com grande volume de dados pode ser manipulada com a utilização de filtros para seleção de intervalo de dados associado com parâmetro QUERY.

    • Deverá executar processo de validação do arquivo de exportação

      • Com o objetivo de garantir a integridade dos dados extraídos deve ser executado o parâmetro CHECKSUM na instrução do utilitário se esse apresentar suporte para o parâmetro.

      • Nesse caso, recomendamos digest SHA-256 [38].

      -----------------------------------------------------------------------
  CHECKSUM=YES CHECKSUM_ALGORITHM=SHA256
  -----------------------------------------------------------------------

    • É possível utilizar a ferramenta sem privilégios administrativos elevados desde que aplicadas permissões adequadas. Abaixo seguem os grants necessários para execução sem privilégios elevados:

      • DATA_PUMP_EXP_FULL_DATABASE e DATA_PUMP_IMP_FULL_DATABASE

      • Deve existir usuário de serviço específico e a senha será passada pelo Control-M.

    • Não exportar as estatísticas do objeto manipulado

      • A melhor prática, recomendada pela Oracle, é a retirada das estatísticas durante a execução do Data Pump para beneficiar o desempenho;

      • A estatística deve ser executa no objeto de destino com a finalidade de melhorar o desempenho das consultas que serão executadas;

      • A execução de REINDEX é uma forma de atualização de estatística e desfragmentação de índice e deve ser avaliada antes da execução em função do tempo de execução, dependendo da quantidade de registros e das contenções gerada no objeto

    A proposta foi dividida em 4 fases:

    1. Exportação (Data Pump) a partir da base de dados do transacional no appliance Exadata.

      1. Deve ser utilizado formato de arquivo binário .dmp para dump.

      2. O arquivo de dump deve ser gravado em estrutura NFS (Network File System) compartilhada entre a instância de origem e a instância de destino, e com acesso restrito.

    2. Importação (Data Pump) na base de dados do ORACLE standalone a partir do arquivo disponível no NFS.

      1. Após importação, deve ser realizada a atualização das estatísticas.

    3. truncate da partição na tabela de origem.

      1. O drop gera necessidade de reconstrução de índices na origem de dados;

      2. Para o truncate não há essa necessidade e o Oracle recupera o espaço previamente alocado em background.

      3. O drop/truncate da partição só poderá ocorrer após a importação do dado no database/objeto de destino com sinalização de sucesso para o Control-M.

    4. Apagar o arquivo de dump original após execução de todas as fases anteriores com sucesso;

      1. Em caso de execução sem sucesso, os arquivos devem ser apagados de forma manual.

    Data Pump export

    Segue template de script para export com os parâmetros necessários para o case apresentado. 

    +-----------------------------------------------------------------------+
| expdp DB_USER/DB_PWD \\                                               |
|                                                                       |
| DIRECTORY=DIR_DUMP \\                                                 |
|                                                                       |
| DUMPFILE=dumpfile.dmp \\                                              |
|                                                                       |
| LOGFILE=logfile.log \\                                                |
|                                                                       |
| TABLES=TABELA:PARTICAO \\                                             |
|                                                                       |
| REUSE_DUMPFILES=NO \\                                                 |
|                                                                       |
| EXCLUDE=STATISTICS \\                                                 |
|                                                                       |
| METRICS=YES                                                           |
+=======================================================================+
+-----------------------------------------------------------------------+
    - DB_USER: Usuário de conexão ao banco de dados.

    • DB_PWD: Senha do usuário de conexão.

    • Directory: Nome do diretório utilizado pelo Oracle, que faz referência a uma localização física.

    • Dumpfile: Especifica o(s) nome(s) do(s) arquivos(s) a serem gerados, que contém os metadados e dados executados.

    • Logfile : Especifica o nome dos arquivos gerado que grava as mensagens de execução do job.

    • TABLES: Especifica que o Data Pump será realizado em modo de tabela.

      • TABELA: Nome da tabela a ser utilizada.

      • PARTICAO: Nome da partição a ser utilizada.

    • REUSE_DUMPFILES: Especifica se os arquivos de dump podem ser reutilizados.

      • DEFAULT: No. De modo a detectar se ocorreu execução anterior e não reaproveitar arquivos remanescentes de execuções anteriores.

      • YES: Utilizar os arquivos já existentes.

      • NO: Caso os arquivos já existam, o Data Pump retorna erro de arquivo duplicado.

    • EXCLUDE: Permite a exclusão de determinados tipos de objetos.

      • STATISTICS: O EXCLUDE=STATISTICS utilizado exclui as estatísticas utilizadas pela otimizador no banco de dados. Desta forma, é necessário atualizar as estatísticas das bases de dados após a execução, conforme recomendado pela Oracle.

    • METRICS: Grava no logfile informações sobre o número de objetos e tempo de execução.

    Data Pump import

    Segue template de script para import com os parâmetros necessários para o case apresentado. 

    +-----------------------------------------------------------------------+
| impdp DB_USER/DB_PWD \\                                               |
|                                                                       |
| directory=DIR_DUMP \\                                                 |
|                                                                       |
| dumpfile=dumpfile.dmp \\                                              |
|                                                                       |
| logfile=logfile.log \\                                                |
|                                                                       |
| tables=TABELA:PARTICAO \\                                             |
|                                                                       |
| EXCLUDE=STATISTICS \\                                                 |
|                                                                       |
| TABLE_EXISTS_ACTION=APPEND                                            |
+=======================================================================+
+-----------------------------------------------------------------------+

    • DB_USER: Usuário de conexão ao banco de dados.

    • DB_PWD: Senha do usuário de conexão.

    • Directory: Nome do diretório utilizado pelo Oracle, que faz referência a uma localização física.

    • Dumpfile: Especifica o(s) nome(s) do(s) arquivos(s) que foram gerados, que contém os metadados e dados executados.

    • Logfile : Especifica o nome dos arquivos gerado que grava as mensagens de execução do job.

    • TABLES: Especifica que o Data Pump será realizado em modo de tabela.

      • TABELA: Nome da tabela a ser utilizada.

      • PARTICAO: Nome da partição a ser utilizada.

    • EXCLUDE: Permite a exclusão de determinados tipos de objetos.

      • STATISTICS: O EXCLUDE=STATISTICS utilizado exclui as estatísticas utilizadas pela otimizador no banco de dados. Desta forma, é necessário atualizar as estatísticas das bases de dados após a execução, conforme recomendado pela Oracle.

    • TABLE EXISTS ACTION: Cláusula para decisão caso a tabela já exista.

      • SKIP: Deixa a tabela como está e continua para o próximo objeto. É o default.

      • APPEND: Carrega os dados da origem e mantém as linhas existentes inalteradas.

      • TRUNCATE: Deleta as linhas da tabela e carrega os registros da origem.

      • REPLACE: Exclui a tabela existente e recria a partir da origem.
