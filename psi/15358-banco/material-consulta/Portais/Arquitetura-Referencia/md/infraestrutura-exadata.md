# Exadata

## Arquitetura de Solução

1. Esta arquitetura de referência faz parte da Arquitetura completa de multiplataforma CAIXA.

## Objetivo

1. Definição da Arquitetura Tecnológica de *appliances* aceleradores de Banco de Dados Oracle presente no Datacenter CAIXA, com a apresentação das tecnologias envolvidas e seu rebatimento na camada de *backup* .

## Arquitetura

1. A seguinte arquitetura está vigente na CAIXA: ![Figura 1](<./imagem/index-imagem-085.png>) Descrição da imagem - [./imagem/index-imagem-085.md](<./imagem/index-imagem-085.md>) A arquitetura definida visa adequar consolidação das bases de dados Oracle em uma arquitetura especializada para este fim e levando em consideração as premissas do projeto de alta disponibilidade e seu interacionamento com a estrutura de *backup* . Ela conta com a separação dos dados em máquinas de produção (com alta disponibilidade entre sites) e não produção. Para garantir o Disaster Recovery, os ambientes devem ser equivalentes nos 2 sites.

## Tecnologias

1. A arquitetura de aceleradores de banco de dados Oracle é composta dos seguintes componentes:

2. **Exadata** A arquitetura é composta por um *appliance* especializado para banco de dados Oracle denominado Exadata, cujo modelo atualmente em uso em ambiente CAIXA é o X8-Mv2. Trata-se de uma plataforma de *hardware* e *software scale-out* (que permite escalabilidade horizontal, ou seja, adicionar mais nós/nodes), composta de servidores, armazenamento, rede, memória persistente e *software* especializado, o Exadata *Software* , que é o responsável pela inteligência do equipamento. Por ter essa capacidade de adição de nós, deve-se primar pelo crescimento da plataforma fazendo uso de todos os espaços possíveis que se tenha nas máquinas existentes, para isso, deve-se respeitar o limite de 22 nós (independente da composição de nós de processamento e de armazenamento) por máquina. Com essas adições em máquina existente deve-se equalizar as versões de *firmware* entre as máquinas e buscar a configuração de melhor uso do espaço de armazenando dos nós de s *torage node* caso as novas versões possuam tamanho de disco diverso. Os Exadatas possuem 2 tipos de proteção: alto (fator de proteção 3) e normal (fator de proteção 2). Ou seja, no caso de uma gravação de dados este mesmo dado será distribuído em outros 3 ou 2 nós (a depender do fator de proteção). O fator de proteção escolhido para a CAIXA é o alto, por 3 motivadores: equipamentos destinados a rodar banco de dados de aplicações consideradas críticas, o Exadata faz o uso de discos SATA que queimam com mais frequência podendo em casos extremos ocasionar a indisponibilidade do nó caso haja um número elevado de discos aguardando substituição, e por último, há outros equipamentos do tipo *scale-out* no ambiente CAIXA (discos NAS com discos SATA) fazem uso do fator de proteção 3 e, portanto, embasou a decisão pelo perfil de uso CAIXA. A utilização do fator alto permite distribuir as consultas pelos 3 nós onde estão as cópias tornando-se mais performático. O fator de proteção poderá ser flexibilizado desde que precedida de análise dos riscos envolvidos. O Exadata Hybrid Columnar Compression - EHCC é um recurso incluso no Exadata Storage Server e proporciona um alto nível de compressão de dados sobre objetos em um banco de dados Oracle e pode se dar em nível de tabela, partição e *tablespace.* Seu uso deve, uma vez que o banco de dados esteja preparado, ser a regra de forma a obter um uso mais eficiente da solução.

3. **Zero Data Loss Recovery Appliance -- ZDRLA** Além do Exadata, outro *appliance* especialista compõe a arquitetura, o Zero Data Loss Recovery Appliance -- ZDRLA. É uma solução de proteção de dados projetada que ajuda a eliminar a exposição à perda de dados. As alterações nos bancos de dados de missão crítica são registradas no Recovery Appliance à medida que ocorrem, permitindo que os clientes recuperem bancos de dados protegidos para menos de um segundo de quando ocorre uma interrupção ou um ataque de *ransomware* . Dessa maneira a inclusão do ZDRLA na arquitetura CAIXA possui 2 atuações primordiais: redução do risco de perda de dados e endereçar a dificuldades na execução dos *backups* de banco de dados Oracle que eram gravados em área temporária chamada Storage Pool e posteriormente em fita. Sua inclusão na arquitetura permite evitar a lentidão dos sistemas, pois a gravação diretamente em mídias magnéticas ocorria de maneira muito lenta. O *appliance* deve ser utilizado somente como 1ª camada de retenção de *backup* , não devendo ser considerado para retenções mais longas. A volumetria foi projetada para a retenção dos dados por 10 dias embora, caso haja capacidade disponível, pode ser armazenado por um período superior. Com a implementação da nova solução de *backup tapeless* DELL Power Protect o uso do ZDRLA se limitará a ser a 1ª camada de retenção, sendo que para a salvaguarda dos dados se dará diretamente na solução de *backup tapeless* . A conexão entre as soluções Oracle e DELL se dará por meio do RMAN -- Recovery Manager que será responsável pelo envio dos dados para a solução de *backup* e o acesso em caso de *restore* .

4. ***Disaster Recovery*** Para garantir a criação de um *Disaster Recovery* para esta plataforma foi previsto a capacidade do ambiente produtivo no site primário, com o acréscimo de outra máquina, de forma que as cargas sejam processadas de forma balanceada entre os dois equipamentos através da funcionalidade Oracle RAC -- Real Application Cluster, assim, em caso falha de uma das máquinas, a outra assume toda a carga com os mesmos níveis de disponibilidade, sendo necessário o uso do *Disaster Recovey* somente em casos extremos, ou seja, perda total do site primário. A arquitetura proposta está desenhada para ter um cenário de *Disaster Recovery* para o ambiente CAIXA com o uso do Active Data Guard;

5. **Active Data Guard -- ADG** O Oracle Active Data Guard -- ADG endereça as necessidades de criação de ambiente DR -- Disaster Recovery, oferecendo Zero Data Loss Protection a qualquer distância e chaveamento manual ou automático em caso de falha dos nós principais, além de disponibilizar os nós de réplica para consulta pela aplicação. O ADG é suportado a partir da versão 12.2 do Oracle e sua utilização traz benefícios de performance e proteção: ADG - Performance O ADG possibilita a reprodução automática de transações, execução de leituras nos nós de réplica, desonerando o banco de dados principal que fica dedicado às transações e manipulação de dados, execução de backups incrementais mais rápidos e automação de processos de manutenção. Na arquitetura que utiliza o ADG todos os componentes estão ativos, com validação contínua dos dados, diminuindo o tempo de inatividade causado por reinicialização a frio e o custo de ativos ociosos, que estariam somente replicando os dados. Existe ainda a possibilidade de liberação de nó de réplica para extração de relatórios ou execução de testes, contando com dados constantemente atualizados. A partir da versão 19c é disponibilizado ainda o recurso Extend the Footprint of Active Data Guard Applications, onde o redirecionamento DML é executado automaticamente de um *stand by* do ADG para o primário, possibilitando a execução de *inserts* e *updates* a partir do nó de réplica. Este recurso possibilita realizar alterações diretamente no nó de réplica durante uma extração, por exemplo, sem necessidade de alterar inicialmente o nó principal. ADG -Proteção Permite reparo automático de corrupções de blocos, onde o banco de dados detectará o bloco que está corrompido quando lido no banco de dados primário, reparando automaticamente as duas bases usando o nó de replicação, sem qualquer intervenção manual. Da mesma forma, caso seja verificado bloco corrompido no modo *stand by* também será reparada usando a cópia do banco primário.

6. **Real Application Testing - RAT** O Oracle Real Application Testing -- RAT propicia a análise de impacto de alterações do sistema no comportamento das aplicações antes da implantação em produção, conferindo maior controle e segurança a processos de atualizações de *hardware* e *software* , alterações de rede e demais configurações de ambiente. O RAT é composto por dois módulos, Database Replay e SQL Performance Analyzer: Database Replay O Database Replay possibilita a captura de uma carga de transações durante a execução da aplicação em ambiente produtivo e sua reprodução em um sistema de teste ou novo ambiente em caso de migração, permitindo observar os efeitos de uma alteração com carga real sem afetar a produção. Esta reprodução de carga possibilita a avalição de fatores como tempo de execução, dependências, uso de recursos, *throughput* das transações, concorrência, *locks* e demais comportamentos do banco de dados na nova estrutura ou com as novas configurações, antes de implantar no ambiente produtivo ou apontar as transações para um novo ambiente em caso de migrações. É importante ressaltar que para a execução dos testes é necessária a disponibilização de estrutura de servidor e disco, a fim de que o novo banco de dados em caso de migrações ou ambiente e teste reflita o ambiente real da carga capturada. Para realização da cópia fiel do banco de dados atualmente em produção é necessária extração de *backup* pontual com o banco de dados parado, para *restore* na base de teste, ou utilização de *hotclone* para estruturas de banco de dados em containers com utilização de *Multitenant* . SQL Performance Analyzer O SQL Performance Analyzer -- SPA, permite identificar alterações de desempenho de consultas SQL, capturando as consultas da produção (incluindo seus planos de execução e estatísticas) e testando sua execução de forma seriada antes e depois das mudanças. Compara os planos de execução e estatísticas de performance e aplica somente para execuções que forem benéficas, de forma automática ou não de acordo com as configurações, mantendo versões das coletas de estatísticas enquanto conveniente. Existe a possibilidade de uso do Quick Check, ou verificação rápida que disponibiliza métricas de comparação como geração de *buffer* , tempo de CPU, custo de otimizador de plano de execução, entre outras, podendo ser coletadas para todo o banco ou para tabelas ou *schemas* específicos. É indicado para mudanças que impactem os planos das consultas como upgrades, estatísticas do otimizador, criação de índices, entre outros, diminuindo os impactos de regressão de performance em mudanças de cenários. Pode auxiliar em processos de migração de estrutura, upgrades e aplicações de patches, alterações de parâmetros e configurações, adequações de índices, particionamento, *views* , criações de SQL Profiles, entre outros.

7. Assim, o Oracle RAT deve ser utilizado como regra para obter benefícios aos processos de mudanças de estrutura como realização de *upgrades* de versões e aplicação de *patches* , consolidação de bases, alterações de ambiente como servidores, rede e discos, além das mudanças operacionais como implementação de profiles, atualização e aplicação de coletas de estatísticas, parâmetros de otimização, memória, índices, particionamento, entre outros.

8. Sua utilização possibilita ainda a automação das validações de mudanças e redução do tempo durante sua execução.

## Principais Recomendações

1. Os recursos deverão ser instalados no complexo CTC e DTC.

2. Os bancos de dados deverão estar em uma versão suportada pela fabricante Oracle mantendo-se nas versões n e n-2.

3. Utilização do Exadata Hybrid Columnar Compression - EHCC para compressão de dados sobre objetos em um banco de dados Oracle em nível de tabela, partição ou *tablespace* , a depender da arquitetura de referência para de banco de dados Oracle.

4. Realização de expurgo das bases mantendo nos *appliances* somente os dados considerados transacionais.

5. Priorizar o crescimento *scale-out* da solução com adição de nós dentro da estrutura existente, caso haja espaço (limitado a 22 nós por rack).

6. Os databases deverão ser associados a instância e não ao nome do banco de dados, de forma a garantir o balanceamento entre as máquinas virtuais responsáveis pela execução do banco de dados.

7. Fator de proteção alto (3 cópias dos dados).

8. O uso do ZDRLA se limitará a ser a 1ª camada de retenção, sendo que para a salvaguarda dos dados se dará diretamente na solução de *backup tapeless* por meio do RMAN -- Recovery Manager que será responsável pelo envio dos dados para a solução de backup e o acesso em caso de *restore.*

9. O Oracle RAT deve ser utilizado como regra para obter benefícios aos processos de mudanças de estrutura como realização de *upgrades* de versões e aplicação de *patches* , consolidação de bases, alterações de ambiente como servidores, rede e discos, além das mudanças operacionais como implementação de profiles, atualização e aplicação de coletas de estatísticas, parâmetros de otimização, memória, índices, particionamento, entre outros. Utilizar o SPA Quick Check para analisar o impacto de uma alteração do sistema na carga de trabalho do banco de dados antes de fazer a implantação.
