# Apache Kafka

**Importante:** Essa arquitetura de referência se encontra em fase de validação e não possui nenhum indicativo de uso geral pelas equipes. Havendo entendimento que ela se encaixa nas necessidades de seu sistema, a SUART deve ser acionada.

## Arquitetura orientada a eventos

Ao adotarmos arquiteturas orientadas a eventos, adquirimos vantagens como o desacoplamento dos componentes e centralização do fluxo de eventos em um event-store (persistência de eventos).

Aplicando EDA (event-driven architecture), enfrentamos naturalmente uma mudança de paradigma, tornando-se necessário repensarmos a maneira como construímos nossos serviços. Obrigatoriamente, em um contexto EDA, a comunicação deve ocorrer de forma assíncrona, devendo reagir a eventos com fontes heterogêneas compondo um pipeline de execução, normalmente conhecido como event-stream.

Cada evento é processado nas circunstâncias do cenário o qual ele ocorre, contendo informações relevantes de execução (payload do evento), sendo gerenciado de acordo com os limites do contexto onde está inserido. Eventos podem desencadear comportamentos específicos de uma aplicação, refletindo a maneira de como os processos de negócio funcionam.

## Apache Kafka

O Apache Kafka é um sistema de mensagens rápido, escalável e tolerante a falhas que permite a comunicação entre produtores e consumidores usando tópicos baseados em mensagens, de forma simples, o Kafka é uma ferramenta para o processamento de fluxos de eventos que são representados na forma de mensagens. O Kafka recebe uma mensagem indicando um evento e a encaminha para todos os interessados em recebê-la.

## Benefícios do Apache Kafka

O Kafka possui três conceitos principais, que são:

- Produtor: sistema que gera um evento;

- Consumidor: sistema que recebe a mensagem do Kafka.

- Tópico: local onde as mensagens são armazenadas.

Os conceitos acima são comuns a vários sistemas de fila, porém o Kafka fornece vários benefícios que o diferem de outros sistema de fila:

- Confiabilidade – Kafka é distribuído, particionado, replicado e com tolerância a falhas.

- Escalabilidade - O sistema de mensagens é dimensionado facilmente e sem downtime.

- Durabilidade -As mensagens são persistidas no disco, fazendo com que não sejam perdidas smesmo com a reinicialização do sistema, seja em uma finalização normal ou por causa de algum erro.

- Desempenho − Kafka tem alta taxa de transferência para mensagens. Ele mantém um desempenho estável, mesmo que muitos TB de mensagens sejam armazenados.

- Streams: o Kafka possui suporte ao processamento de stream de dados nativo, incluindo transformações e operações como agregação e junções.

- Balanceamento de carga: Possui um mecanismo próprio para distribuir as mensagens em diferentes processos que estão inscritos no mesmo tópico, mas que não devem receber mensagens repetidas.

- Paralelismo: Permite que diferentes processos se conectem a um mesmo tópico, o que possibilita que diferentes processos recebam as mesmas mensagens.

### Tópicos

Um fluxo de mensagens pertencentes a uma determinada categoria é chamado de tópico. É aqui onde as mensagens são armazenadas.

### Partição

Um conceito bastante importante relacionado aos Consumer Group são as partições. Um tópico do Kafka pode ser composto por uma ou mais partições, que são divisões dentro de um tópico.

Quando uma mensagem chega a um tópico, ela será alocada em uma partição do tópico, e apenas um consumidor por grupo pode estar conectado a uma partição por vez. É com esse mecanismo que o Kafka evita que mais de um consumidor de um grupo leia a mesma mensagem.

#### Réplicas de partição

As réplicas nada mais são do que backups de uma partição. As réplicas nunca são dados de leitura ou gravação. Eles são usados para evitar a perda de dados.

O Apache Kafka escolhe uma réplica de partição em um broker líder usando o Zookeeper.

O broker com a partição líder controla todas as escritas e leituras das mensagens da partição.

A partição líder é a responsável por propagar as mensagens para as suas réplicas nos diferentes brokers.

Uma réplica seguidora (follower) que está em sincronia é chamada de ISR (in-sync replica).

Se uma partição líder falhar, o Apache Kafka escolherá uma nova ISR para ser líder.

Os consumidores não consomem mensagens dos seguidores (followers), os seguidores só existem para redundância e failover.

### Brokers

Os Brokers são sistemas simples responsáveis por manter os dados publicados. Cada broker pode ter zero ou mais partições por tópico.

### Clusters

O cluster Kafka é um conjunto de nós que funcionam como uma instância única do serviço de mensagem. Um cluster Kafka é composto por vários brokers.

### Produtores

Produtores são entidades que enviam dados para um broker Kafka.

Toda vez que um produtor envia uma mensagem para um broker, o broker simplesmente anexa a mensagem a uma partição. O produtor também pode enviar mensagens para uma partição de sua escolha.

### Consumidores

Os consumidores são entidades que leem dados de brokers.

Os consumidores se inscrevem em um ou mais tópicos e consomem mensagens publicadas extraindo dados dos brokers.

### Grupos de consumidores

Consumer Group é a ferramenta utilizada pelo Kafka para balancear e distribuir as mensagens de um tópico entre diferentes consumidores. Um consumidor do Kafka deve sempre participar de um grupo, e um tópico do Kafka pode ser acessado por diferentes grupos de consumidores. Isso definirá como o Kafka vai enviar as mensagens para os consumidores.

Se existirem dois ou mais consumidores em um mesmo grupo, o Kafka vai enviar as mensagens para apenas um dos consumidores dentro do grupo, isto é, a mensagem de um tópico será lida por apenas um consumidor de cada grupo.

O Kafka tenta sempre balancear o número de mensagens enviadas para consumidores de um mesmo grupo.

Normalmente, consumidores de um mesmo grupo são diversas instâncias de uma mesma aplicação, que foram criadas para acelerar o processamento das mensagens.

Já consumidores de diferentes grupos leem as mensagens independentemente dos outros grupos, isto é, as mesmas mensagens serão enviadas para todos os grupos. Normalmente utilizamos grupos diferentes para aplicações diferentes.

Dentro dos grupos, não existe duplicação no consumo das mensagens, cada mensagem é lida por apenas um consumidor daquele grupo. Esses controles são feitos internamente dentro do Kafka, sem que tenhamos que implementar nada na nossa aplicação.

Se houver mais partições do que consumidores em um grupo, alguns consumidores terão várias partições.

Se houver mais consumidores do que partições, alguns consumidores não terão partições e ficarão ociosos.

### Mensagem

A unidade de dados em Kafka. Cada mensagem é representada como um registro, que compreende duas partes: chave e valor. A chave é comumente usada para dados sobre a mensagem e o valor é o corpo da mensagem. Kafka usa os termos registro e mensagem de forma intercambiável.

Muitos outros sistemas de mensagens também têm uma maneira de transportar outras informações junto com as mensagens. O Kafka 0.11 introduziu cabeçalhos de registro para essa finalidade.

Como muitas ferramentas no ecossistema Kafka (como conectores para outros sistemas) usam apenas o valor e ignoram a chave, é melhor colocar todos os dados da mensagem no valor e usar apenas a chave para particionamento ou compactação de log. Você não deve confiar em tudo que lê de Kafka para fazer uso da chave.

## Rebalanceamento

O Kafka sempre faz o rebalanceamento dos consumidores e das partições automaticamente, sem que tenhamos que fazer nenhuma configuração especial para isso. ]

O rebalanceamento é feito em três situações, quando um novo consumidor entra em um grupo, quando um consumidor é finalizado e avisa o Kafka que ele saiu do grupo e quando um consumidor para de responder por um longo tempo.

Neste último caso, o Kafka controla quais os consumidores estão ativos utilizando um mecanismo chamado heartbeat . Com ele, os consumidores mandam uma mensagem para o Kafka de tempos em tempos dizendo que continuam rodando e, se essa mensagem para de ser enviada, ou se o consumidor está com algum problema e demora muito tempo para enviar essa mensagem, o Kafka assume que o consumidor parou de funcionar, e assim faz o rebalanceamento das partições.

## Chaves em mensagens

Em grande parte das aplicações, a ordem das mensagens não é importante. Nesses casos não precisamos definir as chaves no Kafka, pois assim as mensagens serão alocadas em qualquer partição e o processamento será em qualquer ordem. Porém, em algumas aplicações, a ordem das mensagens pode ser um requisito essencial, como nos casos de ordens de operações bancárias ou no fluxo de um workflow.

Nesses casos, temos duas opções para garantir a ordem das mensagens do Kafka: a primeira opção é utilizar apenas uma partição, o que não é o ideal, pois com apenas uma partição não conseguiremos processar as mensagens em paralelo e perderemos todas as vantagens oferecidadas pelo Kafka.

A segunda forma é definir chaves para as mensagens, com elas, o Kafka garante que todas as mensagens que compartilham a mesma chave sejam enviadas para o mesmo tópico para serem alocadas sempre na mesma partição.

## Reprocessamento de mensagenss

Uma funcionalidade importante do Kafka é fazer retentativas no consumo das mensagens, isso porque o processamento de uma mensagem pode falhar por algum problema na aplicação. O mecanismo padrão de reprocessamento padrão pode fazer o processamento das mensagens ficar bastante lento, pois ele tentará reprocessar uma mensagem várias vezes antes de continuar lendo as mensagens do tópico.

Como slução padrão, deve-se sempre existir um tópico que será responsável apenas por tentar processar mensagens que tiveram erros, liberando o tópico principal para processar apenas as mensagens que não tiveram erros, para que seu consumidor não fique bloqueado.

## Administração do Kafka

O Kafka permite que programaticamente através de sua API, sejam realizadas operações para alteração e sua estrutura e de seus metadados, seja através de criação, deleção ou alteração de tópicos, ou outras ações similares.

As equipes de desenolvimento não devem em situação nenhuma fazer uso da API de gerenciamento do Kafka para realizar alterações em sua estrutura ou metadados.

Todas as alterações necessárias devem ser realizadas pela equipe de infra estrutura (CEXXX), cabendo as equipes desenvolvimento apenas solicitar tais alterações.

## IBM Event Streams

O IBM Event Streams é a solução de Kafka gerenciado adotada pela Caixa.sipsi

O IBM Event Streams é uma plataforma de streaming de eventos baseada no Apache Kafka.

O IBM Event Streams fornece um conjunto de funcionalidade adicionais ao Kafka, em que se destacam:

- Uso do [Apache Strimzi](https://strimzi.io/) que possibita a implantação em cluster kubernetes, tornando-o assim uma solução altamente resiliente.

- Interface adminsitrativa que permite o gerenciamento dos clusters kafka.

- API Rest que possibilita a produção de mensagens por qualquer aplicação que possa se comunicar via REST, possibilitando dessa forma, um grande aumento nas possibilidades de origem de eventos.

- Um Sistema de registro de schemas, que possibilita a definição de contratos para os formatos de mensagens entre produtores e consumidores (semelhante a um swagger).

- Configurações avançadas de segurança.

### Event Streams Producer API

O Event Streams fornece uma API REST para ajudar a conectar seus sistemas existentes ao cluster Kafka do Event Streams.

Usando a API, você pode integrar Event Streams com qualquer sistema que suporte APIs RESTful, sendo possível produzir eventos utilizando uma conexao HTTP segura.

### Kafka Connect

O Kafka Connect é uma ferramenta criada pela Apache que se encontra siaponível no IBM Event Stream. Com ele é possível a conexão com fontes externas e o tratamento de volumes altíssimos de dados, podendo assim tanto receber quanto enviar dados para essas fontes.

O Kafka Connect usa conectores para mover dados para dentro e para fora do Kafka.

Conectores do tipo " *source* " importam dados de sistemas externos para tópicos Kafka e conectores do tipo " *sink* " exportam dados de tópicos Kafka para sistemas externos.

Existe uma grande variedade de conectores, alguns dos quais são suportados exclusivamente pelo IBM Event Streams.

Para detalhes de quais os conectores se encontram disponíveis, consulte o [catálogo de conectores](https://ibm.github.io/event-streams/connectors/) do IBM Event Stream

## Kafka com Azure Event Hubs

### Azure Event Hub

Os Event Hubs do Azure são semelhantes ao Apache Kafka, pois são uma plataforma de streaming e um serviço de ingestão de eventos. É uma plataforma como serviço (PaaS) totalmente gerenciada e com pouca configuração. A grande diferença entre os Event Hubs do Azure e o Apache Kafka é que os Event Hubs são uma solução 100% cloud, não tendo nenhuma contrapartida para instalação local.

O Event Hub do Azure trabalha com vários protocolos, sendo um deles o protocolo KAFKA, o que permite que qualquer cliente Apache Kafka se conectar à um Hub de Eventos como se fosse um tópico "normal" do Apache Kafka para enviar e receber mensagens.

A seguir estão alguns dos pontos importantes sobre Kafka nos Events Hubs

- Não executam/hospedam brokers Kafka

- Suportam Kafka implementando o Protocolo Kafka:

- O mesmo mecanismo que suporta Kafka, também suporta AMQP

### Event Hub API

Os Event Hubs fornecem um endpoint compatível com as APIs de produtor e consumidor do Apache Kafka que pode ser usado pelos aplicativos clientes do Apache Kafka existentes.

Portanto, aplicativos clientes Kafka podem usar o endpoint Kafka dos Event Hubs sem alterações de código, alterando somente as configurações.
