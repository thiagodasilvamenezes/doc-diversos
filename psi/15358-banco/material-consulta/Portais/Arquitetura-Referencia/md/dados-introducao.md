# Introdução

- No acesso a dados em aplicações Batch, seja para inserção, deleção ou atualização é obrigatório o uso da cláusula commit, onde o valor deverá ser definido em conjunto pelas equipes de DBA do desenvolvimento e produção.

- A camada de dados é responsável pelo armazenamento de dados garantindo integridade, disponibilidade, confidencialidade e documentação.

- A modelagem e a documentação da camada de dados dos aplicativos Corporativos devem ser efetuadas na ferramenta Power Designer, onde é construído o modelo de dados físico, e o respectivo dicionário de dados.

- A camada de dados deve ser acessada somente por componentes da camada de aplicação, sendo vetado o acesso direto às bases de dados por usuário ou pela camada de apresentação.

- Para novas soluções corporativas são utilizados os SGBD SQL SERVER, ORACLE ou APPLIANCE DE SGBD, que são considerados os SGBD Corporativos.

- A definição da camada de dados deve ser realizada pelas Equipes de Administração de Dados, em conjunto com a Equipe de Desenvolvimento, a partir do modelo conceitual e deve seguir as seguintes diretrizes básicas:

- O SGBD DB2 (plataforma alta), quando autorizado o uso da plataforma alta;.

- Os SGBD ORACLE ou SQL SERVER devem ser utilizados para aplicativos desenvolvidos para a plataforma baixa;

- Para a construção de Bases de Business Intelligence (Data Warehouse e Datamart) e de bases de Integração de dados com processamentos em lotes deve ser utilizado o SGBD SQL SERVER. Devem ser evitados processamentos de registros individuais e cursores. As bases informadas no subitem anterior devem ser modeladas preferencialmente de forma multidimensional.

- O uso de APPLIANCE DE SGBD deve ser indicado pela SUART.

- O componente do SGDB stored procedure pode ser utilizado apenas em casos específicos, quais sejam:

- Ou, casos que exijam um controle refinado de commit no escopo da transação: Em que existam dependências entre duas operações para efetuação do COMMIT e que a operação não possa ser garantida de outra forma;

- Ou, apresentem ganho extraordinário de desempenho, acompanhado de relatório exaustivo de testes e números comprobatórios. Em caso de ganho de desempenho, a utilização de stored procedure deve se restringir à consultas atômicas (comando SELECT), específicas e especificadas, sendo vetado qualquer uso que fuja desse cenário. O mesmo se aplica aos componentes trigger e function, que não devem ser utilizados na efetivação de regra de negócio dentro do SGDB.

- A decisão pela utilização de stored procedure deve previamente eliminar as seguintes situações: Acesso à camada de dados por componentes outros que não pertençam à camada de aplicação; Uso de stored procedures encapsuladas ou aninhadas (chamada de uma SP por outra SP); Utilização de stored procedure em tabela de log; Stored procedure não armazenada e versionada em plataforma correspondente (Endevor para a alta e GIT para a baixa); Stored procedure sem rastreabilidade de usuário, sistema e canal.

- Para o desenvolvimento de soluções de ETL, tanto para integração quanto para replicação e ou migração de dados deve ser usada a suíte Informática PowerCenter.

- No caso de replicação em que a origem dos dados é o SGBD SAP SYBASE ADAPTIVE SERVER ENTERPRISE (SAP SYBASE ASE) é facultado uso do SAP SYBASE REPLICATION SERVER.

## Tecnologias em descontinuidade

- SYBASE IQ

- POSTGRESQL

- IDMS

- CACHÉ

- Uso da plataforma intermediária (Oracle ou SQL Server)
