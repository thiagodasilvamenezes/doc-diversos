# Geração de Logs

A padronização do ambiente de esteira Devops facilita o controle e oacompanhamento de processos, provendo as áreas de maior autonomia emaior capacidade de responder rapidamente a problemas, mudanças eincidentes.

## Representação da Solução

![Imagem](https://arquiteturati.dep.caixa/25.06/logs/logs/img/log/log_slf4j.jpg)

{: width="100" style="display: block; margin: 0 auto"}

As aplicações Java devem usar o FACADE SLF4J para escrita de logs e escolher entre os frameworks logback ou log4j 2, conforme preferência das equipes ou necessidades do projeto, como framewor de implementação.

## Características das Soluções

### SLF4J -- Facade de Escrita

O SLF4J é uma facade para escrita de logs nas aplicações Java independente do framework de log utilizado como implementação, permitindo transparência e padrão nas escritas de log e independência dos frameworks.

- API abstrata para escrita de logs

- Fornece acesso genérico aos principais frameworks do mercado.

- O framework escolhido fica em tempo de deploy da aplicação e não em tempo de escrita do código.

- O SLF4J funciona como uma facade e os frameworks como implementações.

- As melhores práticas de mercado indicam usar o SLF4J para escrever os logs, independente do framework utilizado.

- Os frameworks podem ser trocados ao longo do projeto sem impacto no código.

- **Versão a ser utilizada:** 1.7.35 em aplicações Java 8 ou Java 11

### **LogBack -- Framework**

O Logback é o mecanismo de log padrão que é usado pelo Spring Boot e é usado automaticamente quando localizado no caminho de classe. A maioria dos iniciadores do Spring Boot depende transitoriamente do **Logback** por meio de spring-boot-starter-logging.

- Biblioteca escrita pelo mesmo desenvolvedor que criou o log4j

- Biblioteca padrão do SpringBoot

- Framework com melhor performance em velocidade e memôria

- Auto reload de configurações em tempo de execução

- Possui implementação nativa do SLF4J.

- Fácil recuperação de falhas de I/O sem necessidade de restart do servidor de aplicação

- Documentação extensiva.

- **Versão a ser utilizada:** Aplicações Java 8 versão 1.2.10, Aplicações Java 11 versão 1.3.0

### **Log4J 2**

Framework de registro de log em aplicações Java mantido pela Apache.

- Evolução do framework log4j

- Permite log de texto (String) ou log de Objetos

- Tem performance próxima ao logback

- Auto reload de configurações em tempo de execução

- Oferece suporte a expressões Lambda

- Suporte ao Garbage-free-logging que evita a criação de vararg arrays e a criação de Strings quando realizar logging de sequência de chars.

- API mais confiável para logging assynchronous.

- Documentação extensiva.

- **Versão a ser utilizada:** 2.17.1 para aplicações Java 8 ou 11

## **Level de Logging**

Dentre as boas práticas de logging é importante o conhecimento dos níveis de log a serem utilizados e em qual contexto. O level logging é a forma de filtrar informações críticas sobre o sistema, daquelas que são puramente informativas. Usado da forma correta, aumenta a agilidade do suporte quando necessário e evita a fadiga com informações desnecessárias.

### ** Níveis de logging na CAIXA**

A CAIXA irá utilizar 4 níveis de log conforme listados abaixo:

- **INFO**

- **DEBUG**

- **WARNING**

- **ERROR**

Segue abaixo um detalhamento de quando utilizar cada nível:

- **INFO:** Nível padrão de log, que indica uma informação sobre a aplicação. As informações logadas com esse nível, devem ser puramente informativas, sem detalhar a operação realizada que gerou aquela informação. Exemplo de uso: API de Autorização informar o usuário que solicitou a autorização, informar se a autorização teve sucesso ou não.

- **DEBUG:** Mais granular e com informações mais detalhadas sobre uma operação, que permitam identificar problemas na execução de uma operação específica da aplicação em ambiente de testes para checagem geral do funcionamento.

- **WARNING:** Nível de log que indica que algo inesperado aconteceu com a aplicação, nesse caso ou um problema ou uma situação que possa impactar algum processo, mas não deve ser usado para falhas da aplicação. O nível warning deve ser utilizado em situações inesperadas, mas o código continua funcionando. Exemplo: erro de parsing que gerou falha no processamento de um dado para um documento.

- **ERROR:** O nível de log error deve ser utilizado quando aplicação encontra uma falha que impede que uma ou mais funcionalidades responda corretamente. Exemplo: Conexão não disponível para concluir transação.

Em resumo segue cada nível de log:

- **INFO:** Um evento ocorreu e é apenas informativo, deve ser ignorado em operação normal.

- **DEBUG:** Usado para captura de eventos uteis na fase de testes da aplicação. Por padrão o level DEBUG estará habilitado nos ambientes de DES e TQS. Nos ambientes de HMP e PRD, em caso de exceção será avaliada a necessidade pelas equipes responsáveis.

- **WARNING:** Comportamento inesperado na aplicação, mas a mesma continua funcionando e seu core operacional.

- **ERROR:** Uma ou mais funcionalidades não está funcionando corretamente.

### **Informações que NÃO devem ser registradas em LOGS:**

No registro de logs das aplicações dados pessoais, dados bancários, informações de tokens não devem jamais ser escritos em logs, não importando o nível de criticidade da mensagem.

Os registros de logs não podem ser gravados em tabelas de banco de dados, apenas informações de trilha de auditoria podem ser gravadas em banco de dados.

### **Logging de aplicação e Trilha de Auditoria:**

A trilha de auditoria, conforme **TE197 -- Segurança para o desenvolvimento e manutenção de sistemas** , deve ser utilizada apenas para informações relevantes ao negócio sobre aquela transação, fornecendo registros históricos pré definidos para futuras apurações, registrando informações, como: identificação de quem realizou a transação, origem da transação, data e hora de realização da transação e o tipo de ação realizada de forma objetiva(inclusão, alteração, consulta ou exclusão). O registro de trilha de auditoria é imutável em referência aos dados da transação.

O logging por sua vez deve ser utilizado sobre ótica de fornecer informações do comportamento da aplicação, considerando as informações apresentadas acima para cada categoria de logging.
